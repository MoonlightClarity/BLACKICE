## Instrumentation, bounded and observational

The new library lib/startup-critical-trace.mjs creates one unique local JSON file per launch at <profile>/diagnostics/startup-critical/launch-<UUID>.json. It writes an explicit INCOMPLETE initial state before profile startup; an unclean exit leaves its last durable checkpoint. Terminal outcomes are ready, failed or interrupted. Asynchronous atomic checkpoints with file sync run every **1.5 seconds** by default, not once per receipt; hard bound 48KiB, maximum 160 retained samples with explicit discarded-sample counter. Progress samples record relative monotonic time, current stage, total/dispatched/validated, pending operation kinds, oldest pending age, CPU and event-loop delays. Histograms and top-12 slow anonymous operations preserve evidence after completion. File write/drop/failure health is explicit; log warnings are code-only and rate-limited, never receipt contents. Source identity binds version and SHA256 of actual packaged code files plus aggregate runtime-source fingerprint, process/monotonic origin and SHA256 of profile/executable paths. Source Git commit is explicitly null rather than invented from version.

lib/startup-timing.mjs records nested parent-child spans with AsyncLocalStorage, phase outcomes and errors, without changing success/failure semantics. lib/ledger-startup-metrics.mjs marks lease/enumerate/scan/sort/recovery. DirectExecutionJobs traces enumeration, stat, **open**, **read**, close, parse, schema validation, SHA256, index and recovery; pending queues, histograms and concurrency avoid treating overlapping awaits as wall time. For true open/read distinction, traced startup uses open()/FileHandle.readFile()/close(); the untraced path remains unchanged. All ordinary-file/symlink/size checks, complete history validation and receipt hashing, lease, race guards, drain-before-recovery and interrupted no-replay behavior remain. The handle-based mode is a **specific independent Windows review risk**, not a previously proven performance optimization.

lib/direct-execution-api.mjs wires the trace only into startup; server.mjs marks HTTP listen; desktop/main.mjs captures profile, actual renderer-ready-to-show and desktop-ready milestones, and begins the trace before profile recovery. lib/diagnostics.mjs exports compact safe trace health under startupCriticalTrace in existing support snapshots. There is no UI-first/partial-admission behavior change and no new network/security feature.

## Limits and evidence

Same-thread checkpoint timers cannot run during a synchronous event-loop block. After resumption the completed synchronous operation and late timer wake are available, but an abrupt crash inside a blocked parse can leave only the preceding checkpoint. No ETW/kernel, storage-driver, antivirus filter or scheduler evidence is recorded. If the first trace write fails no durable trace can exist; a code-only console warning and support status are used when available. Source hashes are marked unverified if runtime packaged files cannot be read; root must validate build identity against exact installer bytes.

Existing .98 direct-job/startup-focused tests passed **57/57, no failures** (verification/startup-trace-20261115-existing-focused.tap). New focused tests exercise deterministic open-vs-read stalls, nested phases, durable incomplete state, stat permission failure, parallel read-failure drain with closed handles, Unicode data preservation, bounded 160-sample history, and no per-receipt disk writes. A six-run artificial 285-receipt component comparison (15,207,566 bytes, identical state hash bb7fd4f8049f7bf29c8fb5e41e6264faa86f689572164ddb117fa04afce28828) yielded baseline median wall **151.237ms**, traced **157.082ms** (~3.9% component overhead); process CPU **141ms vs 219ms**. Files verification/startup-tracing-20261115-overhead.mjs and .json contain the first raw comparison. A second six-run same-source sample (verification/startup-tracing-20261115-overhead-final.json) showed **baseline median 437.748ms and traced 283.929ms**, with baseline runs ranging 318.556–628.527ms. This reversal is a strong warning of **unmatched host/cache load**, not evidence that tracing accelerates startup. Neither sample supports a precise overhead percentage or a physical bottleneck claim. Artificial small history and no installed GUI mean **no whole-startup result or prediction**.
