# Follow-up measurement gates

## Preserved-history startup

The copied receipt scan is a component experiment. It excludes lease acquisition, recovery writes, Electron launch, server initialization, browser restoration and model/provider readiness. It cannot explain the historical 325.7-second direct-job initialization or establish launch-to-ready improvement.

Do not interrupt an active run or restart for measurement. Once the authorized workload is settled, preserve the entire profile and receipt history and verify the backup/restore boundary. Record exact executable version, source commit and application fingerprint; history count, byte count and receipt hashes; queued/running work; process tree; memory pressure and other host load; OS and Node/Electron versions; storage location; and whether the launch is a warm restart or the first launch after an independently observed OS restart. Do not label a cache cold without evidence or flush system caches as part of ordinary validation.

Collect at least three comparable baseline and three candidate launches. Use an instrumented baseline with the same validation and history, changing only the bounded reader count for a component comparison. Separately retain measurements of the actual installed release. Record monotonic launch-to-ready, every startup phase, detailed ledger phases, validated/enumerated receipt counts, recovery writes and failures. Aggregate I/O sums overlap and are not wall-time components. Process CPU and event-loop counters include unrelated work. Compare distributions, ranges and outliers; retain unsuccessful starts. Verify unchanged authoritative history and expected idempotency/recovery behavior after each start. No model work or external effects may be admitted by the measurement procedure. Until these conditions can be met, whole-startup improvement remains unverified.

## Real job-search outcomes

First reconcile existing runs, exact tool receipts, prepared branches and employer acknowledgments. A model summary alone is not a confirmed application. An acknowledgment can confirm an outcome without establishing which click or runtime caused it; retain that attribution uncertainty. Existing active work must continue under its original application scope and deadline. Do not replay submissions, interrupt it, extend its window or admit a duplicate test.

Maintain a private evidence table per employer/requisition and attempt: run/version/model; authorized window and constraints; start/end times; model turns; attempted/completed/failed tool calls; error codes and host dispatch evidence; distinct recoveries and their outcomes; preparation reached; abandon/defer reason; exact submission-action receipt if available; independent destination/email acknowledgment; duplicates; and unresolved external effects. Preserve originals and distinguish reported, observed and independently confirmed states.

Compute confirmed submissions per elapsed hour, elapsed time to first confirmation, completions per attempted eligible application, abandonment reasons, failures per tool call, recoveries that reached a verified next state, duplicate effects and unresolved-effect counts. Count pending prepared applications separately. Compare multiple completed runs, not one success. Report model/provider, selection scope, destination difficulty, history and time-budget differences; historical runs provide observational evidence, not a controlled causal comparison.

Prospective repetition belongs only within an authorized job-search window, uses eligible destinations that have not already been submitted to, and preserves the user's existing constraints. It must not create test applications or expand the deadline. Release evidence should state which outcomes came from the old runtime and which from the candidate, and list remaining failures independently from improvements.
