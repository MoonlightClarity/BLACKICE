# Swarm project management — isolated source candidate

Status: **source implementation for independent review; not integrated, installed or released**. Introduced from BLACKICE `2.39.97` source commit `2371578ed97960a235abbdd3dbdec14da91a4703`. This is a project coordination board, not the recursive Planning/Goal/Directory runtime.

## Purpose and boundaries

BLACKICE Swarm lets the local user and authenticated **OAuth-grant-scoped connector clients** update one durable project-management ledger. A connector grant is shared across its ChatGPT chats; the current host provides no separately verified chat or worker identity. The **Planning navigation tab** is replaced with **Swarm**. Existing Planning graph, Goal, Directory, and executable Projects stores, routes, records and deep links are intentionally untouched. Existing `#planning` can still open as a legacy link; no Planning tab is shown. Swarm does **not** run an assignment, send a message to a worker, run a model, submit an application, merge a branch, start a release or install an app.

A project contains a coordinator, workers with declared scope and optional bound connector ID, work items with owner/dependencies/requirement revision, explicit coordination phases, source observations, evidence, readiness requests, coordinator decisions, and integration records. Creating a work item **proposes** it; `queued` is an explicit *recorded decision*, not evidence of dispatch; `delivered` requires a reference but is **reported**, not confirmed; `accepted` is a worker/local-human acknowledgement; `completed` requires coordinator approval and a recorded integration reference plus scoped evidence. `completed` means completed in this **management ledger** only, not packaged/live execution. The external action must be checked independently.

### Control surfaces

| Surface | Read | Write |
|---|---|---|
| Local authenticated browser UI | `GET /api/swarm`, `GET /api/swarm/projects/:id` | `POST /api/swarm/actions` with `mutationId`, exact `action`, expected entity revision, and action-specific `value` |
| ChatGPT connector | `blackice_swarm_read` | `blackice_swarm_write` with `planning:write` scope |
| Native short-lived worker | Not yet independently exercised/wired to these new tools | Not claimed as implemented |

The connector **read** response exposes `self.id` as the host-authenticated **OAuth grant ID**, alongside `identityScope.kind = oauth-grant`, with `individualChatVerified = false` and `individualWorkerVerified = false`. A coordinator may register that grant ID as a worker's `actorId`, but multiple chats (or multiple logical worker records) bound to the same grant cannot be isolated or separately attributed by this candidate. For `delivered` reports, `accepted` transitions and readiness requests, a nonhuman caller must match its recorded bound **grant** (not a distinct worker-chat identity); the local human can act directly. Coordinator/human-only operations include queuing, ready decisions, recording integration and completion. Other workers can propose, record source/evidence and inspect assignments, but cannot assert another owner's delivery or readiness; all events identify the host-authenticated actor. No caller-provided actor override is accepted.

The data is saved only to the separate `swarm-board.json` under the existing application data directory. It has a serialized write queue, per-project/item/source optimistic expected revisions, stable actor-scoped mutation-ID deduplication, atomic temp-file rename, and a hash-chained append-only event log within the saved snapshot. Corrupt snapshots **stop loading without deleting the original**. Recorded source revisions and old requirement definitions are preserved; stale evidence remains visible. These checks prevent ordinary lost updates **within one running server**; there is no cross-process file lock or proven multi-host distributed transaction.

## Future architecture (Dylan/root direction; NOT implemented by this candidate)

Swarm is intended to evolve into a **project control room**, not just a board. It has a dual-purpose, potentially always-on but explicitly switchable orchestrator: (a) a dot-like assistant *inside* BLACKICE helping its human user; and (b) a bidirectional development partner assisting the external dot. Its success measure is lower real status/handoff/recovery effort, not accumulating status cards. Multiple concurrent orchestrators are an explicit requirement, addressing the perceived one-agent limitation of Codex.

Partition information into workspaces/tabs **by the actual work**. Each workspace should own its own orchestrator(s), assignments, evidence, events and integration state, with narrowly scoped cross-workspace overlap/conflict detection and one explicit shared release/integration owner. The early layout is **Board + Assignment details + Updates + Integration queue**, with an honest **Orchestrator On/Off** and **Needs attention** surface. Board: scope, owner, running/interrupted state, exact source/process/next step, dependency/overlap, **last verified** activity, sent/delivered versus acknowledged receipt. Details: responsible conversation, evidence establishing versus not establishing the claim, authority/authenticity/applicability revision, stale and failed state. Integration queue: evidence-bound accept/return decisions, overlap, stale-claim and duplicate detection.

An eventual orchestration protocol must persist verifiable assignment **sent / delivered / acknowledged** receipts, expose real worker state rather than inferring it from UI/chat names, deliver actual test/commit/review events, and support bidirectional create/revise/message/pause/stop/priority/review controls **only where a corresponding host action actually exists**. Unsupported actions, uncertain outcomes and pending external effects must not be displayed as success. Recovery should prefer an observed Pause control when present, then **Continue in the same Chat**, and only then create a new Chat after explicit failure; never replay an uncertain action without reconciling receipts.

**Not currently present:** autonomous or always-on orchestrators, per-workspace multiple orchestrators, verified worker process/Chat identity, assignment transport and acknowledgment, worker messaging/pause/stop/priority control, independently observed execution/test/commit notifications, evidence-linked integration acceptance queue, cross-workspace deconfliction, a release controller, and end-to-end recovery automation. The current ledger implements a narrower project record and local/connector updates; it must not be represented as the future orchestration system. Root dot remains the sole integration/release owner.
