# Canonical direct outcome read projection

Direct execution receipts are projected beside canonical intent and runtime state as `directExecution`. They never modify TaskStore, canonical journals, criterion completion, admission, or operation dispatch. Reading never syncs a newer intent snapshot or replays an uncertain effect.

- `CanonicalTaskPlanSource.projectState(state, {client})` requires an authenticated OAuth grant, reauthorizes read before and after the atomic outcome-store snapshot, and derives the owner/source binding from that grant. The saved source revision, epoch, and digest are compared to the supplied canonical state; mismatches remain labelled stale.
- `projectAttachedState(state)` is host-local only. It uses an active explicit native attachment, checks its client and deterministic canonical binding, reauthorizes the stored grant, then rechecks attachment generation. Missing/detached/mismatched bindings add nothing. Never expose this callback to forwarded remote readers.
- `DirectTaskOutcomes.readPlanProjection` atomically reads the exact owner/source binding, distinct host-confirmed measurements, UNKNOWN states, and allowlisted dispatch/evidence metadata. Forms, raw semantic subjects, tokens, private operation arguments, and raw evidence are not projected. A confirmed prior baseline is not a new outcome; a dispatched receipt is not rewritten to success.
- ChatGPTPlanningAPI accepts `planSource` and passes its authenticated caller. RemoteAgentAPI accepts the same service only with an explicit `resolvePlanningClient(remoteClient)` mapping. Remote credential IDs are not OAuth IDs; without a verified mapping, projections are omitted.
- Workspace lists accept `planSource` plus `planningClient`, or trusted-local-only `projectAttachedPlanningState`. Lists return compact measurement summaries, not full binding/operation detail. If the canonical summary revision raced the detail read, that row omits projection rather than mislabelling it.

Server integration (owned by integration lane): inject `directExecution.planSource` into ChatGPTPlanningAPI; assign it after directExecution initialization for RemoteAgentAPI. For authenticated local desktop list/detail routes, pass `projectAttachedPlanningState: state => directExecution.planSource.projectAttachedState(state)` or decorate the detail directly. Do not pass this callback to forwarded remote routes. Native relay_task read integration can call projectAttachedState on its read response; never write the decorated response back to TaskStore.

The Planning UI displays a separate disclosure, labels stale source revisions and UNKNOWN/unresolved effects, and explicitly preserves canonical completion. Existing same-revision snapshot adoption accepts refreshed evidence without discarding draft intent. This change does not add automatic scheduling or retries.

Verification: canonical-direct-projection tests cover actual host-confirmed outcome projection, UNKNOWN/no replay, native edit refresh and stale reads, owner isolation, remote realm separation, revoked access, explicit attachment/detachment, baseline evidence, and unchanged canonical state. Renderer tests cover visible disclosure, escaping, stale/UNKNOWN labels, and provenance checks. Broader source/outcomes/API/workspace/UI regression tests are run together.
