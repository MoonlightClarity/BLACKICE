# Editable SVG visuals

## Structured design and review checklist

The on-demand guide supplies eight checkpoints: intent, visual direction, structure, color plan, construction, craft, rendered review and delivery. Each names a decision or check, the evidence to look for, and a repair. The checklist is used during work, not pasted into every answer. It separates user requirements from the agent's own design choices and forbids claiming a pass without observations. Focused retrieval includes only the relevant additional illustration, data, UX or analysis checks; general retrieval retains the cross-domain set. Asset previews return six concise review prompts alongside the images, so the inspection step is not dependent on remembering an earlier long guide. These are instructions, not an automated aesthetic score or a mandatory host approval gate.

Research consulted November 14, 2026:

- [Valve's Dota 2 character art guide](https://help.steampowered.com/en/faqs/view/0688-7692-4D5A-1935): separate silhouette, value and color review; test against the actual play view. Dota-specific body gradients and color prohibitions are not universal SVG rules.
- [Riot's Clarity in League](https://www.leagueoflegends.com/en-us/news/dev/clarity-in-league/): recognition, facing direction, attention hierarchy and visual noise. Its champion identity rules are not copied as constraints on unrelated art.
- [Valve's Illustrative Rendering in Team Fortress 2](https://steamcdn-a.akamaihd.net/apps/valve/2007/NPAR07_IllustrativeRenderingInTeamFortress2.pdf): coordinated shape, lighting and material decisions, with purposeful reduction of high-frequency detail. The checklist does not prescribe TF2's style or rendering technology.
- [NN/g's visual design principles](https://www.nngroup.com/articles/principles-visual-design/): scale, hierarchy, grouping, balance and legible contrast for UX.
- [IBM Carbon data colors](https://www.carbondesignsystem.com/building-blocks/data-visualization/color-palettes): distinguish category, quantity and divergence. IBM's exact palette is not imported into BLACKICE.
- [Hermes concept-diagrams](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/creative/concept-diagrams/SKILL.md): explicit construction checks are useful, but template compliance, fixed typography and mandatory diagram primitives do not establish art quality. This implementation uses original wording and keeps BLACKICE's static SVG profile.
- [Render-in-the-Loop](https://arxiv.org/abs/2604.20730): the authors report that naively adding incremental visual feedback to off-the-shelf models is suboptimal and train visual-code feedback behavior. This is a limit on the recommendation: a checklist and previews do not establish that BLACKICE's selected model can apply the critique effectively. It is not evidence that this particular model or candidate has improved.

A valid XML document, clean text diagnostics, and a completed checklist are not evidence of improved aesthetics. The paired spaceship evaluation uses fresh workspaces, identical prompts/model/effort and Directory Off in both arms. Inspect the rendered outputs, revisions, guide usage, time and tokens; report a diagnostic pair as such rather than a statistical or cross-domain quality claim. Release remains held while this quality investigation is underway.

## Asset design hardening from the spaceship trials

The observed no-Directory trial produced one transparent spaceship in about 195 seconds and reported a clean 512px preview. The Directory trial completed in about 17 minutes 36 seconds, creating three assets while working through a recursively expanded task and repeated previews. The first inspected asset had a stronger silhouette, but the final comparison acknowledged that the later pair had not been inspected side by side. Its context interpreted the user's A/B-test remark as work to establish another chat and compare variants. These observations do not establish a causal benefit from Directory: the prompts differed, the runs shared a workspace, and the Directory run consulted the other run's history. The selected module configuration also differed. User evaluation identified poor color use in both.

Rendered inspection on light, charcoal and mid-value backgrounds exposed specific design problems: many similar steel-blue shades and weak small details in one asset; broad bright teal panels competing with the focal features and dark edges disappearing on charcoal in the other. Both could return zero text-layout issues because neither contained visible text. A clean parser or text-bounds report was being mistaken for aesthetic evidence.

Professional 2.5D is now the default across artwork and report presentation, unless the brief requests flat or playful work. Explicit safe SVG paths supply thickness, overlap, contact shadows and material highlights; the validator is unchanged. Report depth belongs to meaningful grouping surfaces and subject illustrations, with crisp typography, quiet borders and accurate flat data marks. The general guide includes an art-direction method even without Planning or Directory: operationalize style as proportions, contours, materials, lighting, palette roles and detail scale; decompose the image into connected masses and layers; assign shared material value ramps; budget accent area and contrast; inspect at deployment size. Examples are reasoning contrasts, not required styles or palettes. A single asset should not acquire a separate workflow branch for each drawing decision. Directory now resolves named sibling dependencies as well as numeric and canonical IDs. Previously a dependency such as shared_brief was silently discarded, so the next worker lacked its prerequisite record. Duplicate, unknown, forward, self or malformed dependencies now retain the original objective as one bounded work item, with a recorded diagnostic, instead of admitting a partially disconnected plan. Explicit independence and omitted chronological dependencies retain their meanings. Planning instructions discourage splitting one artifact into design-decision tasks or treating evaluation context as authorization for extra deliverables; work instructions keep brief-only steps within their stated completion criterion. These prompt changes are a behavioral hypothesis, not enforced proof that a model will respect scope. A fresh-worker integration regression verifies that named prerequisite content actually reaches the dependent worker.

For assets, call `preview` with `inspection: "asset"`. The ordinary preview remains, followed by a review sheet on three labeled backgrounds, 256/64/32px fit boxes and a grayscale view. This is one preview operation and adds an image only when requested. It uses the same bounded SVG validation and disposable sandboxed renderer. It does not rewrite source, remove opaque backgrounds, add an artifact revision, alter export colors or add chat chrome. All preview results explicitly report that design quality is not assessed; no heuristic palette score or pass/fail art gate is invented.

The first useful regression is a text-free low-contrast asset: text diagnostics can remain clear, but the returned assessment must not certify quality, and the contact sheet must show its unchanged appearance against distinct backgrounds. Native/direct tests cover the optional image channel, no embedded base64 in text feedback, read-only use, invalid modes and malicious SVG. Real Chromium checks cover the three background pixels, output dimensions, rendering and window disposal. Existing SVG history/export remains unchanged.

For a controlled quality follow-up, use identical independent briefs with fixed model/effort and no cross-run history. Compare old/new guidance within each Directory configuration. Blind-rate a dark-scene ship, a light-scene organic prop and a branded UI asset at actual size. Separate silhouette/material/color judgments; record latency, tokens, guide retrievals, repeated previews and revisions. A palette-only revision and a geometry-only revision help distinguish color hierarchy from shape construction. The current change verifies the review mechanism and instruction delivery, not a measured improvement in future model output.

Figures stay in the chat transcript. There is no dedicated tab, empty gallery or permission toggle. A quiet Inspect figure control opens the existing editor with revision history, SVG/source/text export and zoom. The capability is available by default; the agent should use it selectively. Existing saved SVGs and their versioned renderers are unchanged.

Presentation references inspected for this refinement were Heuer and Pherson's concept/argument maps and comparison figures, and the US Government's March 2009 *A Tradecraft Primer*, especially the assumptions comparison (printed page 8), evidence matrix (15), alternative futures figure (35), and timeline (38). The implementation borrows readable hierarchy, light fields and restrained color, not source illustrations or a mandatory technique taxonomy. The visual tool's `describe` action supplies a problem-specific design guide, including custom SVG, uncertainty, bounds, legibility and negative examples. Analysis remains one craft chapter. General SVG guidance and illustration, data and UX chapters broaden the capability beyond analytical figures; examples teach construction rather than required templates.

Visuals are optional conversation artifacts. They do not run Planning modules, launch workers, validate evidence or change Goals. The same service backs `relay_visual`, `blackice_visual` and Chat's inline figure inspector. Native provider conversations retain their original tool catalog; start a new provider conversation to obtain a newly introduced tool. Existing conversations can still inspect and edit visuals through Chat.

## Choosing a representation

Start with the analytical question and the relationship that is hard to see. Arrange claims, observations, dependencies or alternatives so the relationship becomes inspectable. Mix primitives as needed. No technique names or mandatory analysis sequence are exposed.

- “These three reports might all come from one witness.” Draw source dependencies; three reports need not be three independent observations.
- “Both explanations fit the outage; what should we check?” Show shared evidence, uncertainty and the missing observation that separates the explanations.
- “What has to happen before this action is possible?” Show dependencies only if branching matters. A short ordered list usually wins for a simple sequence.
- “Compare exact prices and dates.” Use a table. A diagram would make exact lookup harder.
- “What is the answer?” Give a sentence when one sentence settles it. Do not manufacture a canvas to justify using the tool.

There is no opt-in gate. Availability does not mandate a visual in every answer; prose and ordinary tables remain the better choice when spatial structure adds nothing. A visual never makes an unsupported claim more certain. Label hypotheses, uncertain relationships and missing evidence in words; color alone is insufficient.

## Shared contract

Call `describe` for a complete editable example. Actions are `describe`, `preview`, `list`, `read`, `changes`, `create`, `revise`, `patch`, and `export`. Direct calls require a stable `requestId`; writes also require one in native calls. Direct calls name an existing conversation; create/revise/patch additionally reauthorize the existing files:write grant. Native identity comes from the host and cannot be supplied by the model. `revise` and `patch` require the exact `expectedRevision` read. A conflict returns 409 and never merges unseen user changes. Read, reconsider the correction, then submit an intentional revision with a new request ID.

Version 2 documents have `title`, `summary` (the text alternative, including an analytical takeaway when applicable), and `kind`:

| Kind | Editable content |
| --- | --- |
| `composed` | `width`, `height`; `items` with unique IDs, labels, optional positions/dimensions and status; labeled directed `links` with optional uncertainty; `groups` with member IDs or explicit bounds; `grid` columns/rows; `notes`; bounded custom SVG `regions` |
| `custom` | A static `svg` string, title and a sufficient text alternative |

The compiler assigns missing stable IDs and returns the semantic document, deterministic SVG, and a text equivalent. Omit coordinates for local automatic arrangement; optional layout.columns and explicit coordinates control geometry. Small relationship graphs use a neutral ring to avoid routing through a middle object; other content uses bounded packing. Layout does not infer causal or temporal meaning. Group enclosures that include unrelated items are rejected rather than silently implying membership. Version 1 rendering remains unchanged so earlier exports can still be validated. Limits: 40 items, 60 connections, 12 groups, 20 notes, 8 custom regions, 6 grid columns and 12 rows; 32 KiB SVG; 100 artifacts and 200 revisions per artifact within a 20 MiB conversation journal. Split large analyses rather than shrinking labels to fit. Each custom region carries a label and text alternative and is edited as SVG source. It can coexist with semantic objects, but its paths do not claim semantic meaning. Custom content does not claim a semantic round trip. Chat's explicit custom fork creates a separate artifact and retains the original composition.

No additional model calls are used for rendering, reading, editing, history or export. The model pays for its document/tool output and any revisions it chooses. `list` returns metadata and history, not every SVG. Agent `read` omits the redundant rendered SVG; `export` supplies it. Write receipts return assigned object IDs. `changes` provides actor-tagged field deltas after an observed revision (default five revisions, maximum twenty), with explicit truncation of long values and a pagination cursor. Native turns receive bounded ID/revision/actor metadata for saved visuals, so user changes are discoverable without inserting entire drawings into context. Keep artifacts small and purposeful.

## Editing and persistence

Tool availability itself has a prompt cost even when no visual is produced. A full-catalog history fixture crossed its automatic compaction threshold after the schema grew (93,198 estimated tokens against 93,061); compaction added a model call. Its persistence test now uses a larger fixture window, while context/compaction tests retain their own limits. This is not a measured visual reasoning benefit: evaluation must include catalog overhead and any earlier compaction, not just visual tool calls. Rendering and editing themselves remain model-free.

Chat displays validated SVG images directly inside the scrolling conversation. Inspect opens a keyboard-operable dialog with content fields, an advanced JSON structure editor, a draft preview, text equivalent, revision selector and SVG/JSON/text exports. Simple fields edit item labels, statuses, connection labels, groups, notes and grid cells. Simple controls add items and labeled connections. Field edits generate targeted patches where possible; the source editor can add/remove primitives and change positions. Drag-and-drop layout is deferred. Custom SVG source is editable as text. Failed validation and revision conflicts leave the draft in place. An unchanged retry reuses the same request ID. Patches can add/update/remove objects by collection and ID, set document presentation fields, or set an existing grid cell. All operations commit together at an exact expected revision; dangling links and prototype fields are rejected. Removing an item requires removing its links and group memberships in that same patch.

The panel explicitly shows current revision numbers; historical tool receipts retain their original revision identifiers. Historical inspection and export select an exact immutable revision and disable overwriting it. Revisit via the saved conversation. The conversation journal commits revisions and retry receipts atomically using a synced temporary file and rename. Reads validate saved content before allowing export. Data is separate from Planning and Goal stores. Conversation trash retains its visuals with the conversation; permanent data lifecycle integration is deferred and must not be claimed as implemented.

## Renderer boundary

SVG is an encoded image URL, never injected into the chat DOM. Both host and renderer validate the same bounded profile, layered over the existing static SVG validator. Scripts, events, foreign HTML, navigation, external resources, CSS, filters, masks, patterns and reusable references are rejected. Numeric geometry, element count, nesting and byte size are bounded. The host CSP continues to prohibit objects and external image resources. There is no approval dialog for normal safe use. Invalid submissions preserve the previous valid revision. No renderer claims that structural validity proves analytical correctness or legibility.

## Worked decision

An outage follows a deployment. Three support reports initially appear to corroborate a code regression. Put both “code regression” and “load increase” beside the observed failure and draw explicitly uncertain explanatory links. Add a source group showing that the three reports repeat the same monitoring alert. They no longer look like independent corroboration. A note identifies the missing discriminating observation: old and new versions under equal load.

The next action becomes a controlled comparison, rather than an immediate rollback justified by three supposedly independent reports. If equal-load testing finds both versions fail at the same threshold, revise the observations and explanation links. Preserve the earlier revision to show why the decision changed. The diagram's benefit is exposing dependency and a useful test; it does not establish causation.

## Verification and evaluation

Automated checks cover native execution with Planning off, saved catalog restoration, authenticated HTTP/static assets, shared adapter persistence, conflicts, retry identity, cancellation, exact history/export and malicious SVG. `node tests/visual-headless.mjs` exercises the active chat in a disposable BLACKICE Electron/Chromium profile: inline rendering, user edit/addition, preview, agent patch, conflict draft, history and exact SVG export. It never opens the user's browser profile.

To evaluate default availability, run paired tasks with identical evidence and model settings in three arms: prose, ordinary structured text/table, and visual-tool access. Randomize order and blind scoring. Include source dependence, competing hypotheses, causal confounding, branching dependencies, uncertain timelines, and negative controls (a one-sentence answer, exact lookup, a simple sequence). Score correct distinctions, unsupported claims, missing-evidence detection, decision quality and calibration. Measure end-to-end time, tool latency, model input/output tokens, correction turns and SVG retries. Test whether a user can change a label, relationship and grid cell, reopen it after restart and export the same revision without model assistance.

An occasional tool succeeds when users complete requested visual tasks reliably and selected spatial tasks improve beyond the structured-text arm at acceptable cost. Default enablement needs a broader benefit: neutral or better negative controls, no material increase in unsupported certainty, and consistent net quality/time gains after selection and revision costs. Attractive diagrams alone are not evidence. If structured text matches the quality faster, reduce unsolicited visual use. No comparative reasoning improvement has been measured by the implementation tests.

Follow-up increments: richer graphical overlap diagnostics; richer keyboard geometry and connection editing; stable Planning artifact references; per-conversation archive/export lifecycle; optional pinned transcript cards; then a controlled evaluation of automatic selection. Do not gate ordinary reasoning on any of them.

## Integration choices from the design handoff

Included: renderer-managed geometry, stable object edits, actor-tagged user changes, mixed custom regions and concise positive/negative examples in the attached tool description. These reduce authoring and correction effort without requiring the user to learn an analytical taxonomy.

Deferred: a permanent global component marketplace, interactive executable SVG, drag-canvas editing, automatic promotion of generated diagrams into reusable templates, and mandatory Planning integration. None is needed to demonstrate the user-edit/agent-revision loop. Custom regions are static graphics, not mini-applications. Visual tools remain available by default without requiring their use; paired outcome and cost evaluation remains outstanding.

Chat previews remain visible inline. Generated compositions without custom regions receive a subdued grayscale/charcoal display treatment; original SVG export bytes and custom-authored colors are preserved. Workspace controls use BLACKICE's shared theme variables. The model guide asks custom SVG authors to match the surrounding theme and avoid bright decorative fields.

## Rendered authoring feedback

`preview` accepts an unsaved document, or an artifact ID and optional revision. On desktop it returns a PNG and advisory text-bounds/overlap diagnostics without saving a revision or launching another model. The isolated, hidden, sandboxed Chromium surface denies permissions, external navigation and resources; it is disposed after each preview. SVG validation is identical to saved-artifact validation. A server without the native preview callback reports unavailability explicitly. Preview latency and image tokens are paid only when requested. Automated diagnostics do not assess evidence quality, graphical meaning or every possible overlap.

`tests/visual-authoring-render.cjs` checks all three authored examples in real Chromium, clipping and overlapping transformed text on a small canvas, absent viewBox normalization, cancellation recovery and disposal. This verifies rendering mechanics; it does not prove future model outputs or better decisions. Guidance emphasizes a visual argument, deliberate custom composition, clear hierarchy, restraint, and rendered inspection before saving.

## Concrete SVG construction guidance

The on-demand guide now supplies a drawing vocabulary: an 8-unit spacing rhythm, measured text plus padding, explicit line spacing, connector clearance and routing, paint order, narrow-display calculations and valid SVG construction fragments. Fragments show shared dependence, an unknown interval and a displaced long annotation. They are local techniques to combine, not a chart taxonomy or whole-figure templates. The guide rejects decorative text slides, removes automatic all-caps labels and oversized headings, and keeps BLACKICE colors. Full examples use quieter, smaller headings. Saved user artifacts are not restyled.

Research references: [Hermes concept-diagrams](https://github.com/NousResearch/hermes-agent/blob/main/optional-skills/creative/concept-diagrams/SKILL.md) and [Hermes architecture-diagram](https://github.com/NousResearch/hermes-agent/blob/main/skills/creative/architecture-diagram/SKILL.md), inspected November 14, 2026. The useful ideas are explicit construction rules, semantic color, spacing and text fitting. This implementation uses original wording and geometry. It deliberately does not import Hermes HTML/CSS templates, marker references, bright architecture colors, tiny labels, fixed diagram menus or universal box layouts. Its SVG fragments compile and render under BLACKICE's existing static profile.

The tab remains removed. Construction guidance is retrieved only when authoring, not injected wholesale into ordinary answers. Rendered tests verify geometry and compatibility, not aesthetic preference or consistent future model behavior. The latest real custom-SVG test exposed a text-slide failure; checking actual model-generated responses remains the criterion for the next qualitative assessment.

## General drawing and deeper craft guidance

The tool description now advertises requested artwork, game assets, data graphics and static UX studies as well as analysis. A requested creative deliverable does not need an analytical justification. Unsolicited figures still need a communication benefit; availability is not a requirement to decorate answers.

describe without a focus returns a general foundation and three worked constructions. The optional focus argument retrieves illustration, data, ux or analysis depth. These are composable teaching chapters, not a user-facing taxonomy or a limit on drawable subjects. General drawing covers coordinates, path commands, curve handles, silhouettes, negative space, value/color hierarchy, typography, layout, display-size checks, accessibility and revision. The analysis chapter retains Heuer-inspired uncertainty and evidence comparisons. Unneeded specialist chapters are not returned, and none is inserted wholesale into every model turn.

- Illustration explains silhouette-first construction, consistent viewpoint/light, material cues, shape language, restrained detail, asset pivots and small-size checks. The precision optical module example uses coherent projected faces, a raised metal plate, recessed glass, selective bevel highlights and a restrained contact shadow.
- Data guidance specifies source validation, explicit scale equations, zero/log-domain handling, missingness, uncertainty and independent numeric checks. The example derives coordinates from five declared demonstration values and breaks the line across a missing day.
- UX guidance covers task hierarchy, realistic content, spacing, components, errors/recovery, focus/disabled distinctions and narrow-layout recomposition. The example is a fictional save-conflict recovery screen, explicitly not functioning controls.

BLACKICE's subdued colors remain the default for analytical chat figures. Artwork may have its own coherent palette and a UX brief may supply a brand. Existing custom SVG source and saved renderers are not rewritten. The gradient-1 renderer adds bounded local linear/radial gradient paint. Scripts, external resources, CSS, reusable references, filters, masks and clipping paths remain disallowed. Gradient IDs must be unique and resolvable; no inheritance or reference cycles are supported. Prior renderer versions remain registered unchanged. Transparent art is possible by omitting the background shape. Large illustrations, photographs, executable interfaces and games may need another format or tool.

The drawing syntax was checked against [SVG 2 paths](https://www.w3.org/TR/SVG/paths.html) and [coordinate systems](https://www.w3.org/TR/SVG/coords.html). Text-equivalent guidance follows [W3C complex images](https://www.w3.org/WAI/tutorials/images/complex/); this does not claim that a static mockup is an accessible implemented product.

### Verification and remaining quality hypothesis

tests/visual-craft.test.mjs verifies native/direct focused retrieval, schema rejection, bounded static compilation, correct sample coordinate mapping, the missing-data break, persistence and exact historical export. The real Chromium authoring fixture renders all six complete examples and local construction fragments; manual inspection also checks shapes and text-to-mark clearance, which text diagnostics do not comprehensively detect.

This demonstrates executable guidance and compatible examples, not that arbitrary future model outputs will be artistically good. Evaluate unseen prompts under the old and new guidance with the same model/settings: a 48px inventory asset family; an asymmetric vector scene; a CSV with negative values and missing dates; a long-content mobile form with an error; a wide-to-narrow product redesign; and a source-dependency analysis. Score brief fidelity, originality rather than example imitation, small-size readability, numeric integrity, task clarity, unsupported claims, source editability, time, tokens and repair turns. Include a one-sentence answer as a no-visual control. Reject the hypothesis if broader guidance merely makes longer SVGs, repeats the sample lantern/screen for unrelated tasks, raises data errors or adds unsolicited decoration. No paired model-output quality gain has yet been measured.

### November 14 candidate quality trials

Isolated Luna/max runs used the same spaceship request with Directory and Planning off. The baseline took 107 seconds and four previews; the first checklist candidate took 144 seconds and six previews. Manual inspection did not establish a meaningful aesthetic improvement: the candidate remained a flat emblem, and diagnostic variants added work. A checklist is therefore not itself evidence of better art.

After adding professional 2.5D construction guidance and the optical-module example, a candidate took 177 seconds and eight previews. Its hull, canopy and engines showed more dimensional construction, but the final response explicitly reported that the model could not open the preview. This is a single exploratory result, not a controlled quality win or a release acceptance result.

A separate native response-only probe correctly identified the same PNG's pale body, teal canopy and aft engines, and identified weak engine attachment. A minimal dynamic-tool probe delivered inputText and inputImage parts but the model reported no visible image. An explicit-forwarding probe reported that the tool result arrived as a text string. These observations narrow the feedback failure; they do not establish that the renderer, provider or model alone is responsible. Release remains pending a working image-feedback path and final verification against the exact release source.

The code-mode shape probe exposed newline-separated text and PNG data URLs. Extracting those URLs and forwarding them with the image helper restored image recognition in the minimal probe. The actual visual-tool definition and callback then also succeeded: Luna identified body/cockpit colors and engine positions and proposed a margin correction, using two preview calls. The guidance now supplies this recipe in the tool description, describe response and preview metadata. This is a bounded compatibility instruction, not a native-runtime rewrite or proof that every client uses that representation. Structured clients retain the original image parts. Thirteen focused regressions and the native six-example rendering fixture pass; end-to-end authoring quality remains separately evaluated.

The fresh feedback-enabled authoring trial completed in 123 seconds with two previews and a real visual revision. A second construction-guidance trial completed in 135 seconds with two previews. Both remained generic top-down sprites in manual review; recognition at 32px was not sufficient evidence of the requested professional finish. Older guidance favoring dark silhouette/inset planes was replaced, and bounded local gradient paints were added as a construction capability. This capability passes 72 focused visual tests and native gradient-pixel checks, but its effect on fresh model artwork is not yet established. No release acceptance or broad aesthetic improvement is claimed.
