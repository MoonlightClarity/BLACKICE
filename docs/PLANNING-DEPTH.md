# Substantive planning and reasoning acceptance

> **Status: Historical documentation.** This preserved release-era design, evaluation, or migration record is **not current usage guidance or deployment evidence**. Do not infer present defaults, tool contracts, or installation state from it. See [current documentation](README.md) and [source release notes](../RELEASE-NOTES.md).

## Purpose

The strongest useful deliberation is a quality goal, not a separate technical guarantee. At this historical evaluation, modes were **Forced**, **Advisory** and **Off**: Forced gated actions on applicable planned work, Advisory did not require that gate, and Off disabled automatic planning requirements. These are not the 2.39.81 Chat controls. See [current On/Off modules](MODULAR-PLANNING-ONTOLOGY.md). Response length and provider reasoning effort remain independent controls. An atomic request may have one action; a complex request needs the material questions and checks that can change its result.

This contract addresses ceremonial compliance: a plan exists, a comparison is named, and work is marked done without demonstrating the substantive operation. It does not certify private reasoning or semantic correctness.

## Reserving judgment

A familiar task type supplies candidate methods, not a settled account of this instance. Keep consequential framing, diagnosis and remedy choices provisional until the actual request and evidence support them. Preserve established facts and decisions the user has fixed. A clear bounded operation needs no invented uncertainty.

The plan commits to work that can resolve the live choice. Its `result` names the planned work product or desired operational state, rather than a predicted analytical finding. Its `doneWhen` must allow an inquiry to complete with confirmation, refutation or a bounded unresolved result. Its `evidence` records what was actually found. A negative diagnosis can complete an inquiry; it does not complete an unachieved repair or delivery, whose actual acceptance criteria still apply. Later operations that depend on an unresolved choice should stay conditional until the relevant finding determines them.

For example, “rewrite the request helper to stop duplicates” assumes the cause; “locate the source of duplicate invocations and apply the corresponding repair” leaves that cause open. The latter still needs the actual trace and repair. Merely writing neutral language or saying a hypothesis is provisional does not establish openness to evidence.

Saved context labels a plan goal, planned output and reported finding separately. Predictions and reported completion are not independent proof. This distinction must survive continuation and compaction, including when automatic planning is Off.

## Enforced work and outcome records

**Current canonical contract (v2, from 2.39.23):** the Plan records cohesive work items, resource/effect scopes, dependencies, instructions and evidence criteria. One work item may require several real tool operations. The host records the actual operation lifecycle separately; it does not require a model-authored leaf and completion note for every read, input or click.

Forced planning requires an applicable owned work item. The host can reject mismatched resources, effects, dependencies, stale plan context and unsupported effect claims. Completion must be measured against the selected criterion using the actual journal: observed sources, destination confirmations or evidence-grounded judgments. A model's `done` label, an attempted submission or a reported outcome is not independent confirmation.

Earlier task-schema-10 plans used a different prospective `result` / `note` / `doneWhen` leaf contract and a single primary dispatch per leaf attempt. That text is preserved in [the historical schema-10 guide](history/RECURSIVE-PLANNING-SCHEMA10.md) for frozen legacy sessions. It is not the instruction set for a new contract-v2 task.

None of these checks independently proves semantic understanding, a fair comparison or that every website accepted the intended result. Runtime receipts show what was observed or dispatched; final claims must stay within that evidence.
## What substantive thinking must produce

For a material decision, the useful intermediate product is a bounded piece of the actual task. Examples include competing paragraphs, a current and proposed design, comparable resource allocations, or rival causal predictions.

Compare the current approach with its strongest feasible rival under the same actual user objective, audience, constraints, and relevant evidence. Keep the work proportional to the point of disagreement; do not duplicate the entire deliverable merely to create alternatives.

A comparison should expose the concrete difference, its mechanism, the expected consequence for the user's outcome, the evidence that discriminates the options, and the condition that would change the choice. Concise records and actual artifacts are both valid. A named technique, alternative label, completed status, confidence label, or extra token count is not the comparison.

Evidence quality and value under the user's goal are different variables. More metrics or easier substantiation can strengthen a claim without making it the best emphasis or action. Conventional presentation, a third-party wish, and an inferred audience cannot silently replace the user's objective.

A revision should respond to a material observation. An unchanged conclusion after a fair check is valid. A negative result, discrepancy, or bounded unresolved finding can be useful; do not require perfection or manufacture a reversal.

## Thinking configuration versus thinking quality

The requested provider effort, the dispatched parameter, the effective value reported by the provider, and visible Think commentary are different evidence. None alone proves substantive reasoning. BLACKICE must not present a plan receipt or visible thinking section as an independently verified quality score.

## Behavioral evaluation

The executable local acceptance fixtures and independent output checks are documented in [PLANNING-BEHAVIOR-EVAL.md](PLANNING-BEHAVIOR-EVAL.md). They prepare tasks and score results without starting a provider. Passing their verifier tests is separate from a model passing the tasks.

These cases are evaluation specifications. Passing deterministic runtime tests does not mean these model behaviors have passed. Evaluate actual decisions, candidate outputs, actions, and use of evidence, not the presence of favored words. Use the same model and explicit effort for paired cases when comparing behavior.

| Pair | Controlled change | Evaluate |
| --- | --- | --- |
| Positioning | Same evidence; broad analyst objective versus an explicitly specialist objective | The scope and weighting follow the actual goal. Compare credible candidate wording before narrowing. Metrics alone do not determine the answer. |
| Compression | Same length pressure; a long section is uniquely informative versus redundant | Compare actual before/after passages, retained value, losses, and reader benefit. The decision responds to information value rather than length alone. |
| Debugging | Same symptom; a discriminating test points to parsing versus rendering | The next operation targets the demonstrated cause. A successful edit alone is not proof of repair. |
| Screening | Same role; an employer preference versus a verified immutable eligibility barrier | The former affects fit or ranking; the latter can exclude only when it is actually binding. Missing information is not a negative result. |
| User constraints | Same options; a real explicit constraint is satisfied versus violated | The action changes for the real gate, without inventing additional gates. |
| Investigation | Same unknown; resolving it would change the next action versus would not | Spend effort on the consequential unknown; proceed when additional evidence would not affect the useful result. |
| Recovery | Same intended effect; a job is pending versus has a verified completed outcome | Do not claim the pending action succeeded or duplicate it merely because its receipt is incomplete. |
| Causal commitment | Same duplicate-request symptom; listener lifetime versus retry condition is the actual cause | The observed cause changes the repair. Compilation alone cannot confirm a suspected cause. Retain the initial explanation when a discriminating check supports it. |
| Contrary evidence | Same expansion proposal; demand is high in both, but capacity is exhausted and funding conditional in one | The recommendation responds to the binding capacity and funding evidence, rather than attaching a risk paragraph to an unchanged expansion recommendation. |
| Criterion stability | Cheapest conversion option loses required comments; the next cheapest preserves them | Preserve the actual requirement and inspect the converted output. Do not redefine success to protect the favorite. |
| Direct execution | Exact one-occurrence typo correction versus an open editing request | Perform the exact bounded edit and verify its diff without adding hypotheses, research or broader rewriting. |
| Fixed approach | User has selected SQLite; valid sample versus duplicate IDs violating the supplied uniqueness rule | Preserve the database choice. Resolve only the concrete import conflict when present; do not reopen the architecture or silently drop rows. |
| Fixed editorial direction | User explicitly requests a shorter version for a stated audience versus an open assessment | Execute the specified direction intelligently; do not reopen the audience or whether shortening is wanted. |
| Confirmed approach | The discriminating evidence supports the initially suspected cause or familiar approach | Keep the supported approach and act; do not manufacture doubt, a reversal or additional research to demonstrate deliberation. |

A polished rationale with the same inappropriate action across materially changed premises is a failure. Report model, effort, inputs, outputs, observed actions, and evaluation limitations before claiming an improvement in reasoning quality.
