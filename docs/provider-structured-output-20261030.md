# Planning schemas on compatible provider requests

> **Status: Historical documentation.** This preserved release-era design, evaluation, or migration record is **not current usage guidance or deployment evidence**. Do not infer present defaults, tool contracts, or installation state from it. See [current documentation](README.md) and [source release notes](../RELEASE-NOTES.md).

Planning response workers already passed their full `outputSchema` to `ProviderRuntime`. The Responses adapter sent it through `text.format`; the compatible Chat Completions adapter previously omitted it. That left an OpenRouter analytical turn with prompt instructions and host validation, even when the selected model advertised structured outputs.

Compatible analytical turns now choose their transport from the exact selected model's provider-reported catalog entry. A fresh cached catalog is reused. A cold or expired cache triggers one existing read-only catalog discovery before inference. Discovery cancellation propagates without starting inference. Other discovery failures produce an explicit `catalog_unavailable` prompt fallback; they do not imply that inference access is unavailable.

| Evidence | Request behavior |
| --- | --- |
| Fresh exact model advertises `structured_outputs`, with a compatible strict schema and safe wire projection | Send a detached wire schema as `response_format:{type:"json_schema",json_schema:{name:"planning_response",strict:true,schema}}`; preserve the original host schema |
| Fresh exact model advertises both `tools` and `tool_choice` but not `structured_outputs` | Use the single forced data-return function described in [Response-only function serialization](provider-response-function-20261111.md); never dispatch it as an action |
| A `uniqueItems:true` constraint occurs beneath `oneOf` | Keep prompt and host validation, with `schema_uniqueness_projection_unsafe`; do not send a projection that changes exclusive branch matching |
| Catalog lists only `response_format` | Keep prompt and host validation; JSON mode alone does not establish JSON Schema support |
| Model absent, parameters missing, catalog unavailable, or schema has optional/open object fields | Keep prompt and host validation, with a specific capability reason |
| The schema-bearing inference request fails, including an error inside an HTTP 200 SSE stream | Surface that failure; do not retry without the schema or switch models/providers |

All object properties must already be required, and each object must declare `additionalProperties:false`, to use this strict transport. The eligibility check does not add requirements or replace optional values. A required property with `anyOf:[<closed object>,{type:"null"}]` is compatible, preserving the nullable representation used for optional accuracy metadata. Empty enum lists are rejected by this transport check. The actual merged five-stage schemas are checked recursively in the wire test suite.

Some compatible provider grammars reject `uniqueItems`. The compatible Chat Completions adapter therefore creates a detached wire copy and removes that keyword from the schema nodes used by Planning. It preserves the original `outputSchema`, the captured Planning contract, every other constraint, property names, and literal data in `enum`, `const`, and examples. Native requests and the Responses API continue to receive their complete original schemas.

Removing uniqueness beneath `oneOf` can broaden a branch so that a previously valid value matches two branches and becomes invalid. The projection detects that ancestry, including through nested properties, array items, `anyOf`, and `allOf`, and declines the provider schema in favor of the explicit host-validation fallback above. It does not invent a replacement grammar.

Planning acceptance remains unchanged: `PlanningBrowserRuntime` calls `validatePlanningModuleResponse` before recording the public response. The user-agency parser calls the existing deterministic user-cost evaluator, whose schema validation rejects duplicate `blockedOptionIds` with `INVALID_USER_COST_DECISION`. Valid unique IDs still pass. The compatible wire projection does not serve as a general JSON Schema validator; callers retain responsibility for the complete host acceptance contract.

OpenRouter requests also set `provider.require_parameters:true` when this schema transport is selected. That field is not sent to generic compatible endpoints. Ordinary requests without the analytical profile retain their existing behavior. An internal analytical context checkpoint clears the stage output schema for its summary request while retaining it on the stage itself.

Capability events identify `provider-json-schema` or `prompt-and-host-validation`, the reason for the choice, and `hostValidationRequired:true`. These describe the request contract, not verified model compliance. An HTTP 200 response can still contain a provider error in its SSE body; transport status alone is not successful inference. OpenRouter's [structured-output documentation](https://openrouter.ai/docs/guides/features/structured-outputs) documents the request format and provider-routing preference, and explains that schema enforcement varies by endpoint. Local structural and reference validation remains authoritative; a schema-shaped response does not prove its factual claims.

The focused tests use fake HTTP responses and native handoff fixtures only. They inspect the actual serialized request body, fresh/stale/recreated-runtime discovery behavior, generic catalog fallback, nullable schemas, cancellation before inference, and the absence of an implicit HTTP or SSE-error retry or parameter downgrade. Additional regressions cover the real Planning schema's wire projection, unchanged source schema, successful unique-ID acceptance, duplicate-ID rejection by the existing host parser, direct and nested `oneOf` fallback, literal-data preservation, and unchanged native schema forwarding. They do not measure model accuracy or call a live provider.
