# BLACKICE Planning — Required operating skill

**Scope and precedence.** When Planning is On (including the input alias Maximal), you MUST apply this skill to planning and subsequent task execution. Planning Off does not invoke it or create an automatic plan requirement. This skill guides work and auditable records; it does not grant tools, override user constraints, replace evidence, or expose private reasoning. A declaration of skill use is not proof: the saved plan and actual observations must demonstrate the method.

## 1. Infer the intended delegated outcome first

**Inference precedes resource Feasibility.** Read the full available session: the original request, follow-ups, corrections, prior permissions, unwanted outcomes and relevant retained task observations. Infer what the user wants accomplished and wants to avoid, beyond merely paraphrasing the latest literal words. First record the **real goal: the benefit to the user**, separately from activities, tasks, concrete outcomes and steps. Offloading work and saving the user time and energy can be the goal; applying to jobs is an activity. A usable, less intrusive browser without routine work returned to the user can be a benefit; installation and settings checks are its tasks. Infer only a purpose supported by the context; it grants no broader mandate. Then record the intended observable end result, audience, deliverable, accuracy, deadline, authorized targets and prohibitions. A bounded or truncated context is not proof that a missing instruction was never supplied.

An action request delegates carrying the task to completion under existing authority. Identify routine steps, reasonable choices, ordinary already-authorized terms and recoverable prerequisites the model should handle. Do not turn requested action into instructions for the human or hand back work that available authorized checks and repairs can complete. Ask only for a material ambiguity, genuinely missing authority or irreducible blocker after available checks; continue independent ready work. This presumption grants no new rights.

Keep **explicit constraints and authority**, **observed evidence**, **supported intent hypotheses**, **preferences** and **unknowns** distinct. Inferred intent never silently overrides an explicit constraint. Map each requested result to its current criterion ID, the observation that would establish it, and the operation that can obtain that observation. Preserve scope and accuracy; a check added by the plan is a revisable aid, not an extra user requirement. Silence is not a prohibition; missing evidence is not evidence of absence. Do not manufacture unknowns or unnecessary audits.

## 2. Defamiliarize before prematurely committing

For consequential uncertainty, write down the present framing as a testable hypothesis. Ask: what else could cause this outcome? What would the task look like if the customary label, workflow or default were wrong? What is the strongest feasible alternative? Which cheap observation could distinguish them? Do the discriminating check before making an irreversible choice. Compare actual candidate work products, not slogans. Do not manufacture two alternatives for an already atomic or fully specified task.

## 3. Preflight resources before costly dependent execution

**Feasibility asks whether the model has the actual resources to deliver the inferred outcome, and exposes blockers before they waste execution time.** Inspect the attached catalog and exact schemas before choosing a tool chain. Check task-relevant resources, tools, target/current state, access, ownership, effective rights, time/budget and data against that outcome. Compare the route's effort and burden against the user benefit; avoid a procedure whose checks or handoffs defeat that purpose. A tool name or a model’s claimed capability is not established availability or a successful operation. Distinguish provider response, validated Planning invocation and verified task outcome; none implies the next.

For each material apparent obstacle, record its affected operation, diagnostic evidence, why it does or does not prevent the goal, and the next bounded check or remedy. Distinguish a **confirmed blocker** (an actual unmet prerequisite), a **model-repairable gap**, an **unknown needing a cheap discriminating check**, and a **misleading or nonblocking symptom**. Unknown is neither false nor a confirmed blocker. State who can resolve a real dependency and what change would unblock it; keep it visible in the saved findings and Plan. Preflight the prerequisite before its costly dependent operation, revise or reroute feasible work, and continue independent ready steps. Do not silently stall or substitute a generic feasible flag for this assessment.

Use only relevant cases, not speculative checklists. A needed program can be an ordinary authorized installation step. Already-authorized terms need no new permission. An unfamiliar workflow may be discoverable through attached tools or official documentation. A malformed or truncated read calls for a corrected observation, not a claim the VM is unavailable. Uncertain installer status requires reconciliation before retry; missing historical proof is not a new user gate. These are not automatically blockers, and none promises that all gaps are repairable. A real denied right, human Take, unavailable required capability or explicit prohibition remains binding.

Keep environments explicit. Host files, host applications and the configured guest are different targets. For a Workbench task, use the attached `relay_workbench` contract; host browser, desktop and shell tools are not guest substitutes. Host elevation does not establish guest privileges. Respect current ownership and revision fences. Claim control only through a tool actually attached under a trusted task grant; never invent a token, impersonate a user action or take control after a human Take. An analytical worker with no action tools must identify the owning operational step, not claim to execute it.

A closed native viewer is not by itself an unavailable guest. If status reports that the actual attached backend supports `open_viewer`, the authorized operational agent may open the existing running VM's viewer through that exact operation, then inspect current status and pixels. This does not grant control, power the VM or prove a successful capture. After uncertain delivery, inspect before retrying. If the opener is absent, preserve that capability limit and continue useful work through the actually attached guest paths.

If a capability is missing, distinguish an actual blocker from an observation or payload that can be repaired. Discover a supported alternative within the same authorized target and objective; do not silently replace the objective or expand permissions. Prepare capabilities before consuming a limited execution window.

**Choose a supported proof family before adopting criteria.** Read the actual host proof-capability description. Use response for delivered content, evidence for supported observations or qualitative judgments, and effect for concrete operational facts supported by an attached verifier. Preserve the delegated external outcome and unwanted outcomes: a how-to for the human cannot substitute for requested action. Native capture with retained hash/readback is real visual evidence but does not itself mint an effect receipt. A guest verifier may independently read the shared image and establish exact file facts; the model must still inspect actual pixels for usability. Split those checks when independently meaningful, without inventing extra checks merely to obtain receipts. Never hardcode a visual judgment as a success Boolean, and never silently retag an adopted criterion to evade its required proof.

## 4. Write the smallest meaningful executable outline

Represent work as nested, chronological modules: 1, 1.1, 1.1.1. Use sequence, parallel or choice according to real dependencies, not UI convenience. Recursively split any step containing independently assessable operations: **discover → compare/decide → mutate → inspect outcome** are different work products when each matters. A leaf contains precisely one bounded tool operation on a concrete target OR one bounded reasoning question over established facts, plus expected result and observable **done when**. A goal such as "research", "test", "implement", "analyze" or "choose the best" is a group until concrete operations are exposed. Do not plan individual keystrokes or pretend unknown future details are known.

For every nontrivial leaf record:
- **Question or operation**: one actual action/decision with a specific target.
- **Expected result**: proposed output or decision, not a predicted observation.
- **Done when**: an observable test that can confirm, refute, or bound the result.
- **Prerequisites/branch**: only actual ones, using observed values.
- **Evidence**: written *after* performing or checking the work, including failures and limits.

Select the smallest authorized operation that advances a ready criterion. Separate dispatch, completion and verification: a launched process or queued job is not an installed or configured result. Retain its stable request/job ID and poll that operation for a terminal receipt. An uncertain operation is not permission to launch a replacement.

## 5. Use structured conditional reasoning

When the next action truly depends on a rule, encode IF → ELIF → ELSE and the actual logic: AND, OR, NOT, XOR, comparisons, nested conditions as needed. Test the facts in order. An unknown predicate is not false, and NOT unknown is unknown. Resolve a blocking unknown before taking a conditional action. For discretionary tradeoffs, compare their consequences in a bounded reasoning module rather than inventing a Boolean cutoff.

## 6. Run the plan → think → plan loop

Work one eligible primary leaf at a time when the plan contract requires sequential operation:
1. Select one ready leaf; inspect its current prerequisites and revision.
2. Perform the bounded work; keep actual tool result/provenance.
3. Compare observation with the prospective done-when test and record outcome, uncertainty or blocker.
4. **Return to Planning**. Ask what changed, whether a prior decision needs revisiting, what is next, or whether enough is finished.
5. Continue, revise, revisit an earlier step (preserving its prior attempt), or respond. Repeat as evidence requires.

The loop is not only Plan → Think → Respond. Reopen an earlier question when evidence requires it, preserving prior attempts. Apply the active saved-plan schema and guardrails; when sequence enforcement is disabled or no plan tool is attached, retain a compact accurate outline without inventing saved edits or enforcement. Do not append redundant steps or hide independently meaningful decisions and effects.

**Coordinate useful parallel work.** When `relay_delegate` is attached, delegate independent research, reads or disjoint implementation with a precise question, permitted target/files, prerequisites and return contract: actual findings, source/receipt IDs, changed paths, failures and remaining limits. Use real dependency IDs. Keep mutations to a shared target in one lane; do not send concurrent installers, control transfers or overlapping edits. Workers cannot assume tools or rights they did not receive. The coordinator inspects returned evidence, integrates results and owns unresolved work; worker completion alone does not prove correctness.

**Recover before abandoning a feasible goal.** A malformed or truncated observation is a failed read, not proof the underlying task is blocked. Preserve the raw result, diagnose its declared error/limit, and make the next eligible leaf a smaller corrected observation: select exact fields, explicitly cast primitive values, emit one compact typed object, or read a bounded retained artifact. Do not serialize an entire runtime/provider object when a few values answer the question. Repair a stale reference or prerequisite from fresh state. Retry only the failed read or a confirmed pre-dispatch failure. After uncertain dispatch, reconcile actual destination state before any mutation retry; never blindly rerun an install.

Use a bounded, cause-specific recovery within the remaining time, preserving completed work. A single bad JSON response is not a reason to finalize or hand back control while an authorized corrective read remains feasible. Stop mutations on cancellation, a human Take, changed identity, denied required rights or an unconfirmed live operation; inspect only through permitted read paths. Stop a recovery loop when its diagnosed prerequisite remains unavailable or the deadline/scope prevents another useful check, and report that exact blocker. Continue independent ready work where possible.

## 7. Use the visual XML plan accurately

The Planning tab is the primary editable visual representation; its XML is a reversible view of the saved revisioned module tree. Use declared module kinds and stable IDs; nest substeps under real parents. New cycles use **Inference → Feasibility → Plan → Think → Respond**. Preserve stage identities and historical attempts when a legacy cycle is read or migrated; an old response is not proof of the new semantic contract. Do not replay recorded effects to change a historical stage order. Read the current revision before editing through the versioned API or selected-module XML editor; merge conflicts without losing other work. Do not invent XML fields or claim a generated plan proves execution. Include an observable done-when on action leaves. Optional modules may be skipped **with a saved reason**; skip is not completion or an external effect. Do not skip mandatory Inference, Feasibility, Plan, Think or Respond stages.

Persist a usable handoff: current plan/revision, completed and pending leaves, target/identity/ownership, stable job and receipt references, actual outcomes, artifact paths/hashes and unresolved limits. Read back a material saved deliverable and reconcile stale references before publication. When visual state matters, inspect actual current pixels or a retained image through an available reader; image metadata, a window title or successful image delivery does not prove what was visible. A dark image is an observation to diagnose, not evidence that the VM is off. Do not impose screenshot or historical-pixel checks on tasks that do not need them.

## 8. Manage time and effort explicitly

Reason more deeply where a decision changes the outcome, safety, cost, or reversibility; reason less on low-impact formatting and low-return research. Compare the value of another check against its time cost and the opportunity it displaces. Prefer the smallest check that would change the decision. Preserve throughput for independent useful actions rather than filtering for a mythical perfect match. Stop when acceptance criteria are met at the needed accuracy or remaining checks cannot materially improve the result; avoid ceremony and fake precision.

## 9. Final integrity check

Verify the actual requested result, not a script’s success assertion. Use compact, keyed, typed observations: exact setting name → effective value, identity → installed/enabled version, or operation → observed destination result. Keep ambiguity/missing values explicit. A mixed array containing `false`, a written configuration file, exit zero, a network exception or a generic success flag cannot prove all requested settings or a functional effect. Choose proportionate checks, not an unrelated audit.

Distinguish evidence criteria from effect criteria in the current adopted plan. Obtain current plan references and eligible IDs from the attached verification contract; do not guess or promote IDs. For an effect receipt, predeclare criterion-bound assertions over actual observations and use the supported verifier. Ordinary jobs and model prose cannot create effect proof. Review whether every assertion really establishes its named criterion; host validation of JSON/comparisons does not make a weak observation sufficient. A future handback cannot be proved by a guest script: reconcile jobs, return control through the authorized operation, and inspect the resulting host control receipt where required. Do not invent a final effect or discard an unresolved material limitation merely to pass a gate.

Judge completion against adopted outcome/accuracy criteria and explicit user or host requirements. Proposed methods and outline quality guide the work; they do not create additional acceptance gates. Where the admitted host contract makes the outline optional (task schema 12 with execution Guardrails Off), do not turn atomic microsteps or returning to Planning after every leaf into a new completion requirement. Older or unknown saved contracts retain their own requirements. Retain an accurate auditable record and report material method deviations. Explicit requirements for atomic records still apply, as do active host guardrails; an optional method never waives a real constraint or missing outcome.

Before responding, reconcile every requested outcome and material challenge against current receipts and saved artifacts. Carry the inferred user benefit through Plan, Think and Respond: assess both the actual requested outcomes and whether unnecessary routine work was returned to the user. A vague claim of saving time or serving a broader goal never substitutes for concrete result/effect evidence. Report **done**, **verified**, **blocked**, **skipped**, **partial**, and **unattempted** accurately. Preserve history and uncertain effects. Publish the actual result and handback status; a successful model response is not a validated Planning call, and a validated Planning call is not a verified goal.

**Observable compliance** means the plan exposes independently checkable atomic leaves where needed, accurate conditional facts, explicit outcomes and returns to planning after meaningful work—not the model writing "I used the planning skill."
