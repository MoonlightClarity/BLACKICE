# BLACKICE 2.33.10

BLACKICE is a Windows app that lets AI assistants work with your files, use websites, and carry out tasks on your computer. Use it from ChatGPT, or choose a supported online or local AI model inside the app.

- **Work with files:** Read documents, edit files, create results, and run commands.
- **Use websites:** Open pages, fill in forms, upload files, and keep sign-ins in the built-in browser.
- **Tackle larger jobs:** Make step-by-step plans, track progress, and split work among several AI assistants.
- **Keep useful context:** Save conversations, notes, instructions, and reusable skills.
- **Automate repeat work:** Queue tasks or schedule them to run while BLACKICE is open.
- **Follow the work:** See actions, results, errors, and file changes as they happen.

## Saved passwords and browser copying

**Settings → Password manager** keeps website credentials in an encrypted BLACKICE vault. For an authorized new-account task, the agent can generate and save a strong password, then fill its exact saved revision into observed HTTPS password fields. The credential tools return an identifier and receipt rather than password text. Generation retries reuse the original saved password; filling does not submit the form. Existing-account login uses a saved credential and keeps MFA or account challenges visible when human action is required.

Choose Chrome, Firefox or BrowserOS Neo as the browser password-manager destination. **Copy to browser password manager** prepares only the selected saved revisions, opens that browser's native password manager, and reveals a temporary import file. Complete the browser's import and select **I imported these passwords** in BLACKICE. The optional automatic-copy setting queues new or changed credentials in encrypted storage; native import still requires the explicit local handoff. The interface distinguishes awaiting import from user-confirmed import and does not claim independently verified synchronization.

Windows exports receive a current-user ACL before plaintext is written, expire after five minutes, and are removed on confirmation, cancellation, shutdown or recovery of an interrupted process. Profile backups exclude this temporary export subtree while retaining the encrypted vault. The plain Node server does not offer password operations without a protected storage implementation. See [BROWSER-PASSWORDS.md](BROWSER-PASSWORDS.md) for use, recovery and compatibility limits.


## Use BLACKICE from ChatGPT

**Settings → ChatGPT connector** exposes direct execution and planning tools to an authenticated ChatGPT client. ChatGPT remains the reasoning interface and receives the tool results in the same conversation; this endpoint does not launch a BLACKICE model worker. It uses the existing public HTTPS remote-access address with a separate `/mcp/chatgpt` route, OAuth authorization, individually revocable grants, and scoped tools. The local owner approves requested connection access once. File changes, commands, browser actions, and attachment imports execute directly within the granted scopes, without a separate BLACKICE per-action approval prompt or policy setting.

Existing OAuth grants and their scopes remain unchanged. Relative file paths use the configured working folder; absolute file and upload paths are supported with the Windows account’s access. File tools do not impose a workspace boundary. Shell commands run with the Windows account’s permissions. Required sign-in and other human interactions can still pause execution. Removing the former local approval gate does not approve or replay old pending, cancelled, or interrupted actions. Old pending approval requests can be cancelled under **Actions waiting for you**; inspect their saved receipts before requesting new work.

Before each request that needs BLACKICE, the installed tool workflow should call `blackice_direct_status` with a fresh harmless nonce using the existing authenticated connection. Check the matching nonce, direct-execution mode, availability, the caller's `connectionId`, and its actual `grantedScopes`; `supportedScopes` describes what the server supports, not what this connection may do. Reuse valid authorization rather than asking the user to reconnect for every request. This check does not expand scopes or prove that an execution action completed.

Execution actions return durable IDs. Within the same OAuth grant, repeating the same request ID with identical arguments retrieves the existing action; an ordinary network reconnect or token refresh can preserve that grant. Compare the authenticated status `connectionId` before retrying. After revocation, replacement, or new authorization changes the connection, do not replay an uncertain mutation through the new grant: inspect the original receipt and effects in BLACKICE first. A pending approval, cancellation request, or interruption is not completion. Inspect the saved receipt and exact result before proceeding; cancellation cannot undo effects already performed. After a process restart, uncertain actions are marked interrupted and never replayed automatically. See [CHATGPT-CONNECTOR.md](CHATGPT-CONNECTOR.md) for the transport, authorization, tool contract, and verification limits.

**Settings → ChatGPT connector** guides setup on this computer. New profiles use standard HTTPS on port 443 without a port suffix; saved 8443 addresses remain supported. In ChatGPT, choose **Plugins → + → Add custom MCP server**, name it **BLACKICE connection**, paste this computer's displayed `/mcp/chatgpt` URL, and use **OAuth/CIMD**. Choose **Create as a plugin → Connect BLACKICE connection**; complete Install only if offered. Match the local approval code. **Select all** checks this request's offered permissions; separately choose **Allow selected access**. No manual client ID, client secret or Owner login key is needed.

In a new ordinary **Chat mode** conversation, type `@BLACKICE` and select **Plugins → BLACKICE connection**. Send the guide's unique status-check prompt and inspect the actual matching nonce, direct-execution mode, availability, `grantedScopes`, `modelStarted: false` and `providerTurns: false`. Confirm the guide only after that result appears in the intended conversation. Source upload or portable package installation alone does not register a native App connection; a Files-only picker is not proof of tool availability.

Reuse healthy grants. OAuth scope consent and ChatGPT's plugin permission are independent. Select **Allow all actions** for this plugin in ChatGPT to permit actions without ChatGPT's per-action confirmation; this does not change global ChatGPT permissions, other plugins, or the BLACKICE grant. BLACKICE has no additional per-action approval setting. The guide checks owned-route readiness, reports pending steps and offers bounded diagnostics; local endpoint success alone cannot verify the Chat conversation. See [the exact setup sequence, failure table and proof boundaries](CHATGPT-CONNECTOR.md). The experimental BLACKICE-to-ChatGPT browser provider has been removed; ChatGPT calls BLACKICE's direct tools.

For production use on Windows, check **Settings → ChatGPT connector → After Windows restarts**. Tailscale needs an **Automatic**, **Running** Windows service and verified unattended mode. BLACKICE needs an enabled background startup entry for this exact profile at the current Windows account's sign-in. Tailscale can remain connected before sign-in; BLACKICE is a desktop app and still needs that account to sign in. Use the offered startup action to configure missing prerequisites. Setup is bundled with the desktop app; Windows elevation is requested only if service repair needs additional permission. Existing Tailscale preferences, related scheduled tasks, disabled or changed startup entries, routes and connector grants are preserved or reported for inspection.

Startup checks inspect and cache actual settings without changing them. A passing settings check is not a cold-boot test or proof that the connection reached ChatGPT. After the next intended Windows restart and sign-in, verify a fresh status nonce through the existing connection. Keep the computer awake and connected for work; saved schedules remain paused after app restart until deliberately resumed. See [production startup and read-only troubleshooting](CHATGPT-CONNECTOR.md#production-startup-on-windows), [Tailscale unattended mode](https://tailscale.com/docs/how-to/run-unattended), and the [Tailscale CLI reference](https://tailscale.com/docs/reference/tailscale-cli).

For everyday email, the Email workspace can open an installed Thunderbird instance or a blank Thunderbird composer. This reuses Thunderbird's own interface and existing account setup without importing its credentials. Himalaya remains the optional engine for automated mailbox access inside BLACKICE. Opening Thunderbird does not embed its window, read its mail, send a message, or grant BLACKICE account access.

The manual Browser workspace also offers **Import into Neo…**. It opens the installed BrowserOS Neo's native import chooser, where the user selects the source browser, profile, and data categories. Neo owns the import and its confirmation. Imported data belongs to Neo's profile; the contained BLACKICE browser and embedded ChatGPT view keep their own sessions. See [BROWSER-IMPORT.md](BROWSER-IMPORT.md) for compatibility limits.

## Shared planning, remote access and background operation

**Planning** replaces the former Methods workspace. It is the live work document used by BLACKICE's agent: objectives, actionable steps, completion checks, dependencies, branches, evidence and worker ownership. Open it from the top navigation or a chat's plan. The outline and mind map show the same saved state. You can edit the goal, add or move work, choose a branch, and change dependencies in the adjacent editor. Narrow screens have separate Plan, Edit and Saved plans tabs.

The design target is a **semi-structured process knowledge graph**. This release supplies action, sequence, parallel and choice nodes; explicit prerequisites and ownership; and references to saved results, evidence and registered artifacts. Titles, notes, expected results, conditions and checks remain human-readable text. The structured relationships support validation and scheduling; free-form content preserves the context behind the work. Workers now expose the saved revision delivered by an actual plan read. The Knowledge workspace now stores typed notes, facts, assumptions and decisions with sources and explicit links. These saved knowledge records remain separate from the execution plan and its completion evidence.

A save uses the revision you read. If an agent or another client changed the plan while you were editing, your draft stays available; review the current values, keep the edits you intend, then save. Execution receipts and historical results remain separate from reported step progress. Editing a plan does not itself start a task or turn a running worker into a completed one. Existing saved method records and older native tool catalogs remain readable for compatibility; new agent work does not require browsing a method catalog.

Typing publishes a short-lived editing notice for the affected step; the unsaved text stays in your browser. The Shared editing section shows the relevant editors and workers, including the saved revision delivered by each worker's actual plan read. A saved correction to relevant work makes the next affected BLACKICE tool action require a fresh plan read. Independent parallel work can continue. An action already underway can finish, and its result includes a notice if the plan changed during it. A read receipt establishes delivery of the plan, not comprehension. The runtime guard covers BLACKICE's attached tools; native Codex built-in shell/file tools and operations performed independently by outside agents remain outside that hard boundary. Use the conversation's direction and Stop controls when active execution needs immediate redirection. See [PLANNING-AWARENESS.md](PLANNING-AWARENESS.md) for the exact scope and lifecycle.

Swarms use this same visual plan. Worker groups show their owner, allowed scope, required inputs, expected result and completion criterion. Ready work can proceed as soon as its real prerequisites are satisfied. An unrelated blocked branch or a busy coordinator does not impose a global wait. A dependent worker still waits for the actual upstream worker to finish and its required work to be reported complete. The delivery template starts one implementation owner and independent specialists; additional writers need explicit disjoint scopes. The coordinator integrates results and owns final external-action receipts.

**Settings → Remote access** connects both people and outside agents to this same workspace. Private mode uses an authenticated HTTPS address on your Tailscale network. Public mode offers an authenticated internet address for clients that cannot join that network; it requires an explicit selection and publication confirmation in Settings. Each browser pairs with an expiring one-use code. Each outside agent receives its own named bearer credential with read, task execution and plan-edit permissions selected separately. Credentials can be revoked individually. See [Remote access and agent API](REMOTE-ACCESS.md) for connection steps, examples and supported MCP versions.

An authorized agent can handle setup without asking the person to relay a code. The installed `BLACKICE remote code --kind agent --scope=read --scope=tasks:write --json` command issues a scoped grant from the running host. `BLACKICE remote pair --url=ADDRESS --code-stdin --name=NAME --output CONNECTION.json --json` consumes it and saves a private per-user connection. The code is the grant; BLACKICE does not ask for a second confirmation after issuance. Commands use the bundled runtime and do not open another app window. Exact Windows executable examples and connection details are in [REMOTE-ACCESS.md](REMOTE-ACCESS.md).

**Run in background** hides the desktop window while keeping the current profile, encrypted model connections, contained tools and task runtime alive. Reopening BLACKICE shows the same running instance. For unattended starts, launch `Agent Desk.exe --headless`, or run `npm run headless` from the source project. This remains the Electron runtime; the plain Node server is a separate developer entry point. Quit stops work and pauses dispatchers. The host must remain on and the process must remain running; this is not an operating-system service.

## Control and recovery

A pending Send or Save for later belongs to its originating draft. You can switch to another chat or New chat while it is pending; returning to the origin restores its pending state or recoverable error. A late response cannot clear a different draft, move the current conversation or put an error in another chat. The originating request still holds its composer against duplicate submission.

Stop retains its execution lease through already-admitted local tool callbacks, including a pending file publication, provider close or native connection exit. Their actual success or failure receipts remain attached to the original run. Late answer text stays withheld, and the same conversation cannot overlap that unfinished work. Other conversations may use independently available execution capacity. The header shows **Working**, **Stopping…** or **Finishing…** while any corresponding work remains; **Ready** follows actual settlement.

A successful runtime reconnect rechecks persisted explicitly queued tasks. User pauses, capacity limits and saved-only tasks keep their existing meaning. A failed reconnect does not dispatch work.

Stop remains available while a direction is being submitted. The interface distinguishes requesting a stop, waiting for active work to finish, a failed stop request, and acknowledged completion. A failed request offers **Retry stop**. The same settlement state follows the conversation through its sidebar, working-chat list and Activity view. A task releases its execution slot only after its work settles, and an unsettled conversation cannot be moved to Trash.

Optional email storage failure leaves the rest of BLACKICE available and reports Email unavailable without replacing the damaged file. Mailbox and search results have Previous/Next page controls, with account, folder and query changes resetting pagination. Removed schedules preserve failed attempt history without leaving jobs waiting for impossible retries. Failed or cancelled swarm workers retain their observed usage, thread identifiers and tool results.

See [RELEASE-NOTES-2.24.1.md](RELEASE-NOTES-2.24.1.md) for these changes and their recovery limits.

## Visual planning modes

On narrow screens the Planning and Reasoning controls occupy separate usable areas. An empty unavailable or missing plan opens Conversation so its answer or recovery action remains reachable. An explicitly chosen Plan pane is retained, and saved steps or notes remain available. Live mind-map updates and resize retain keyboard focus and pan; zoom limits move focus to an enabled control. Workspace cards report dispatcher and maintenance blockers, with unavailable storage taking precedence.

| Mode | Behavior |
| --- | --- |
| **Maximal** | Expanded actionable planning with a concrete method, expected outcome, and completion check for each unfinished action. Uses the highest model-advertised effort when no explicit effort was chosen. |
| **On** | Explicitly requires a current-turn outline before ordinary tool work and the final answer. |
| **Auto** | Default: adapt the plan's detail to the task, including a compact action for a simple exchange. |
| **Off** | Disable automatic planning instructions and the plan-before-answer gate. Preserve saved notes, plans, and results; planning tools remain available on request. |

The choice travels with the draft and effective run. Continuations and retries inherit it unless changed. Explicit model effort stays authoritative; Maximal does not guess supported effort for an external model. More visible structure and model effort are tools for doing the work carefully, not evidence of a measured reasoning improvement.

Outline and **Mind map** show the same saved task hierarchy. The map supports branch focus, breadcrumbs, zoom, and node selection with shared notes and evidence. **Fit width** preserves readable labels; larger maps scroll inside their canvas. **Guide this step** prepares a draft for the agent to revise the selected step. SVG and `.mm` exports retain the actual plan for editing elsewhere. Blackice does not launch Freeplane or maintain a second live map.

See [RELEASE-NOTES-2.25.0.md](RELEASE-NOTES-2.25.0.md) for the visual system, planning behavior, harness identity, and verification scope.

## Task outline and answer sequencing

Send the outcome you want. With planning enabled and a compatible task tool, BLACKICE first shows that goal and **Preparing the plan**. The agent reads the task record, chooses an appropriate approach, and saves concrete steps. A simple exchange can use one useful action with a short completion check. Substantial work can expand progressively into nested sequences, independent parallel branches, and conditional alternatives. Creating a separate Project or applying a prompt template is unnecessary for automatic planning.

The agent works directly in the same durable plan that you can edit in **Planning**. It records observable actions, dependencies, decision conditions, expected results, completion checks, evidence and worker ownership. It can expand or revise the approach as new facts arrive. No catalog selection or separate Methods mode is required. This is a visible work plan, not private model reasoning. Older saved method references and their exact revisions remain readable for existing conversations.

While automatic planning is enabled, before a turn has saved its own outline, the BLACKICE tool gateway permits planning reads and up to four known inspection/discovery calls so the agent can ground its approach in actual inputs. Other gateway operations return `TASK_PLAN_REQUIRED` without running and direct the agent to read the current revision and save its plan. Normal planning updates do not ask the user for another approval. This is a work-sequencing rule, not an authorization boundary or a change to the host's permission system. Answer deltas, complete messages and native agent-message items are withheld until the current turn records an agent-authored action plan. The saved plan event is published before buffered answer text. A final result without that plan fails with `TASK_PLAN_REQUIRED`; it is not published as a completed answer. Actual thread, turn and usage receipts are retained. Cancellation preserves the last durable state and does not release an unplanned answer.

The enabled planning gate applies to tool-capable turns with task schema v4 or later. Older native task catalogs and models without tools remain usable with an explicit planning limitation; their answers do not pass through this new plan gate. Start a new chat with a tool-capable model to use the revised planning workflow. Existing conversations retain their original tool catalog and saved work.

On a wide screen, **Task plan** stays beside Conversation until hidden with **Plan** in the chat header. Below 1180 px, **Plan** and **Conversation** tabs show one surface at a time, with Plan selected for a new structured task. At 600 px and below, the selected step sits in a compact tray so the outline has room to read. Select a row, then **Details** to see its completion check, evidence, result, dependencies, blocker, skip reason, and registered files. **Back to outline** or Escape in the details returns to the selected row. Wider screens show details by default and offer **Hide details**. Long task descriptions have a **Full task** disclosure with the complete original goal.

Expanding or inspecting a branch starts no work. Use Up/Down to move between rows, Right/Left to expand or collapse, Home/End to reach the first or last visible row, and **Current step** to locate the saved current work. Enter on an action opens its details. Selection, collapsed branches, keyboard focus, disclosures, and reading positions survive streaming updates and task switches. A response hidden behind the Plan tab remains unread until it is actually viewed.

Only action leaves count toward completion. Parallel groups describe independent work; they do not launch extra agents. Choice groups require an explicitly selected child before that path becomes active. Unused alternatives remain visible, and skipping one requires a recorded reason. Skipped actions are reported separately from the chosen-action completion fraction. Finishing the selected route does not complete the whole plan while unused alternatives remain unresolved. **Done** needs agent-reported evidence; ending a model response does not finish outstanding steps. Registered file checks confirm bytes, not the correctness of the result.

### Planning and task direction

Choose **Planning** beside the composer for Maximal, On, Auto, or Off. Open **Options** for the explanation of the current choice. Auto adapts the amount of structure to the task; Maximal requires methods, expected outcomes, and completion checks for unfinished actions. The separate **Reasoning** control sets an explicit model-effort preference when the provider supports it.

Planning is saved per chat and travels with a new task, saved Inbox task, or continuation. Changing it affects the next submitted turn, not work already running. Follow-ups adapt the existing outline while preserving completed work, evidence, and external-action receipts. Older saved recipes and API callers can still supply their existing compact, balanced, or detailed hints; the current composer uses the single Planning control.

**Guide this step** appends the selected step and its completion check to an editable message, keeping any existing draft. Review and send that message through the normal composer. **Draft next action** prepares a continuation for an unfinished settled task; it preserves an existing draft. **Make repeatable** opens scheduling setup only after the saved plan is complete. These controls do not silently start or replay work.

### Edit the agent's work plan

Open **Planning** to find active saved plans in an outline of named groups. Choose **Archive** or **Trash** explicitly to inspect historical plans. **New group** creates a group; **Rename / move** changes a plan's display name and group without rewriting its work or an open step draft. Search matches plan names, group names, the chat title, and the objective. Choose a plan to see its outline or mind map, select a step, and edit its title, completion check, dependencies, parent or position. The Objective editor changes the plan's goal and layout. A plan in Trash remains inspectable and read only. Creating work in this editor records a plan; send a chat message or an explicit task request when you want execution.

**Swarms** uses the same named groups and initially shows active saved projects. Rename, move, archive, or restore a saved project from its controls. Its task outline follows dependency order, with explicit prerequisite links and expandable implementation and review attempts. Removing a group preserves its plans and moves them to Ungrouped. See [PLANNING-ORGANIZATION.md](PLANNING-ORGANIZATION.md) for organization, persistence, conflicts, and API details.

Each save uses the exact revision that was shown in the editor. If another client or worker changes the plan, BLACKICE keeps your draft and presents the current values for review. A reported step status is distinct from the worker's runtime receipt. Updating a title or completion report cannot release a dependency whose actual worker is still running.

The former Methods interface is retired. Its saved records, licensed bundled reference material and older tool schemas remain available for compatibility with existing runs. [METHODS.md](METHODS.md) documents that historical contract. New work uses the shared Planning application directly.

## Background email

Open **Settings → Email** or **Workspace → Email setup & drafts**. Browser sign-in connects Google/Gmail or Microsoft/Outlook through a BLACKICE-owned OAuth application registration. BLACKICE manages token refresh and uses Electron encrypted storage, with Himalaya **2.2.1** running in the background. The installed executable is suggested automatically. No app password is needed for this connection. Existing external Himalaya TOML configurations remain available under advanced setup. Registration, successful sign-in, a supported CLI, and a successful mailbox operation are separate states; opening settings never reads the mailbox. See [EMAIL.md](EMAIL.md) for provider setup and the Google Testing token lifetime.

The agent-facing `relay_email` tool can read status, discover folders, list/search mailbox envelopes, read an exact message and save durable local `.eml` drafts. Folder discovery preserves each provider mailbox ID separately from its display name. Message reads return both the original RFC 5322 source and bounded decoded headers, plain text, and attachment descriptions. Each command is bounded, uses argument arrays without a shell, hides its process window, closes stdin and stops its process tree on timeout or cancellation. To avoid the installed CLI splitting a Windows drive letter as a configuration separator, account commands use an explicit relative configuration filename from its own directory; setup still stores and validates the full absolute path. Message reading uses `--raw --json` without `--seen`. List/search results retain the CLI's pending-index count, so an incomplete index is not reported as an exhaustive search. Only a successful requested mailbox operation records account evidence. Configuration, a CLI check and account evidence have distinct UI states; none is a permanent access guarantee.

The message reader displays decoded text and attachment descriptions, with original source behind a disclosure. It never loads message HTML or remote images. **Reply as local draft** prepares the reply address, subject and quoted body. It preserves an existing composer and requires an explicit **New draft** before replacement; saving remains a separate action.

Drafts are saved on this computer, with stable request IDs that deduplicate exact retries and reject changed content under the same ID. They remain readable after restart. The email integration does not send messages, upload drafts, move/delete mail or enter credentials. Its setup is deliberately separate from the durable task Inbox, which is a work queue rather than an email client. No account is selected automatically during this update. See [EMAIL.md](EMAIL.md) for the supported contract and verification scope.

## Typed knowledge and linked evidence

The Knowledge workspace supports **Note**, **Fact**, **Assumption** and **Decision** records. Add sources one per line and connect existing records with **supports**, **contradicts**, **informs** or **supersedes**. Type filters, readable source/link summaries and revision history make the context inspectable. These labels and links are recorded assertions; they do not independently verify a claim.

Links are restricted to the same working folder or globally available knowledge. Saves validate the current revision and all targets together. Self-links, duplicate links and missing new targets are rejected, while historical references survive deletion of a target. Moving a record cannot silently break existing scope rules. Existing notes keep their content and appear as Note; older clients that omit metadata preserve it. Undo restores the complete saved record, including sources and relationships.

## ChatGPT connection and retired browser provider

The supported direction is **ChatGPT → BLACKICE**. The human uses ChatGPT; its BLACKICE connection executes authorized local tools and returns durable results. BLACKICE's own workers use native Codex or configured API models.

## Shared projects and capabilities

Open **Projects** in the desktop header or workspace menu, or find it with **Ctrl+K**. Start with an outcome and concrete steps, each with an expected result and observable acceptance checks. **Ask agent to plan** appends a planning request to your editable Chat draft without sending it. **Edit details** updates owner, priority, due date, tags, notes, and milestones even while a project is active, without changing its execution definition or review receipts. Manual checkpoints are labeled separately from linked steps that passed agent review. Projects retain their acceptance-review workflow; the former Methods tab is removed.

Each task gets an implementation run and a separate reviewer run. A finished response does not complete the task. The reviewer must return an explicit verdict and observed evidence for every saved criterion. Failed checks feed the next repair attempt within the chosen bound. Missing or malformed verdicts, failed runs and exhausted repairs block the task. Dependent tasks wait for passing review; independent tasks can continue. **Pause after current phase** prevents further admissions while preserving work already running. If the final review was already admitted and passes, the project becomes completed while paused, without needing Resume. Execution receipts must match their saved request IDs; conflicting or multiple matching runs block the task instead of adopting unrelated evidence. **Stop all** also pauses projects and cancels active runs. After restart, projects pause and reconcile saved execution receipts instead of replaying side effects.

**Prepare another attempt** waits for original implementation/review runs and their stopping leases to settle, then carries the previous review or runtime failure and implementation report into the new attempt. Long feedback keeps every failed criterion identifiable within the available input budget. A context or history-storage limit produces a visible blocker rather than silent execution. Restored completion requires matching passing evidence and distinct implementation/reviewer receipts; unsupported completion flags recover from a valid backup or fail closed while preserving the saved files.

If an implementation or reviewer recorded an uncertain/confirmed external action, or recovered an older task-state backup, the project saves a durable retry hold. Automatic repairs and fresh manual retries stop; **Inspect original run** opens the held execution so its destination and original conversation can be checked. A separate review may still inspect the existing result and complete the task if its criteria pass. Prepared drafts with no send attempt remain retryable, and independent tasks remain eligible. Reviewers receive the original receipt context and instructions never to repeat delivery.

The agent can use **relay_project** to inspect or create the same shared plans, start requested execution, read evidence and prepare explicit retries. Project workers do not receive that orchestration tool, preventing recursive project creation. Existing native conversations keep their original tool catalog; start a new chat to use newly added tools. Executed task definitions remain immutable so saved evidence cannot be silently relabelled as proving a changed criterion.

Once every task passes review, **Save as capability** retains the method, checks and distinct implementation/reviewer run IDs. **Use as starting plan** creates a new draft for the current folder with no inherited completion evidence. Historical success never marks a new run as passed. Humans and agents can improve that draft together before executing it. Unfinished plans are saved separately per workspace and can be resumed.

Review evidence is agent-reported and scoped to the saved criteria. Different review turns are independent runtime sessions, not a guarantee that a model cannot make the same mistake twice. Inspect the linked runs for consequential results. Projects execute while BLACKICE is open; this update does not install a system service.

## Durable external actions

New agent conversations can use `relay_task external` for an authorized post or other remote action. A stable receipt binds the destination, exact content and checked attachment checksum. **Prepared** means the final content is recorded. Immediately before sending, `attempt` durably records **uncertain**; the agent proceeds only after that write succeeds. **Confirmed** records the observed result URL and evidence after checking the actual content and attachment. Confirmed actions cannot receive another attempt permit, and matching content cannot be prepared under a second receipt ID. Existing native conversations retain their original tool schema.

After interruption or an ambiguous response, inspect the destination before retrying. Confirm an existing matching result, or use `reconcile_absent` with fresh observed absence evidence before another attempt. Uncertain and confirmed receipts survive restart and take priority over stale saved send instructions. Recovery from an older task-state backup conservatively requires reconciliation, including when the backup predates the first receipt; it cannot restore a stale send permit. Concurrent writers use revision checks and live PID/token ownership that is checked again before publication; a slow live writer's lock is never reclaimed just because it is old. Delegated workers inspect and prepare evidence, while the coordinator owns receipt writes and the final send. These receipts guard the permits requested through this tool; generic browser input remains available, and website evidence is agent-reported. They do not independently verify publication or guarantee external service availability or exactly-once delivery.

## On-demand subagents and verbosity

**Configure → Basics → Response defaults** now includes **Verbosity** (Concise / Balanced / Detailed), **Allow on-demand subagents**, and **Parallel subagents** (1–8). Verbosity is a response-style default; an explicit request for a particular length or format takes precedence. The new options affect subsequent agent responses, not an already-running turn. The same preferences can be changed from a chat via `relay_control runtime_set` using `verbosity`, `subagentsEnabled` and `maxSubagents`.

When enabled, an agent can call `relay_delegate` to assign up to eight independent subtasks in one call; at most the selected number execute at once, with a total of twelve child tasks per agent response. Children share the current working folder and selected model, add provider usage, and can use their delegated workspace, attachment, browser, and connected-tool access. New installations leave optional subagents **off** by default to avoid unexpected extra model usage. Saved native Codex sessions retain their original tool catalogs; start a new chat to add `relay_delegate` to one created before enabling it. Stop cancels running children, and unstarted work is not reported as completed.

## Time limits

Each agent response defaults to **No app limit** for total duration, with Codex and API models alike. To set a duration, open the workspace menu's **Time limits**, search `time limits` or `timeout` with **Ctrl+K**, or expand **Configure → Basics → Advanced**. **Agent time limit** controls the whole response. **API inactivity timeout** is separate: it defaults to five minutes without incoming API data, and received bytes, including streamed heartbeats, reset that clock. Either setting can be No app limit; disabling API inactivity permits waiting indefinitely on a stalled connection until you stop it.

Choose a duration and unit, then Save. Positive whole-millisecond durations are preserved exactly, including durations longer than the underlying timer's roughly 24.8-day interval; Relay does not shorten them to that interval. Settings apply to future agent responses. Work already admitted keeps its saved limits, and editing one setting does not replace the other or the conversation-history choice. A timeout's **Time limits** recovery action opens these settings without sending or retrying a message.

Agents can inspect or patch user-requested settings with `relay_control` actions `runtime_get` and `runtime_set`. Send only the changed `runtime` fields: `runTimeoutMs` for total response duration and `providerIdleTimeoutMs` for API inactivity, each a positive safe integer in milliseconds or `null` for no limit. Tools retain their individual timeouts and provider services can enforce their own limits. Stop remains available without requiring a duration to be configured.

Provider generation failures show specific key, quota, rate-limit, endpoint or service guidance. Model access errors are tracked for that model; healthy siblings and the pinned default remain usable. Input-specific errors stay with the failed request. Connection catalog tests do not clear an actual generation failure. Successful generation clears shared connection warnings; the affected model must succeed to clear its model-specific warning. Editing the connection resets its generation diagnostics. Partial replies remain visible and failed work is never automatically replayed.

Model catalogs are searchable and paged, including entries beyond the first 200. Up to 200 selected models are saved per connection. A catalog response proves reachability, not permission to generate; OpenRouter Test also verifies its key. Explicit defaults stay selected if a provider disappears, with an actionable error instead of silently switching providers.

Execution is direct and trusted. There are no agent permission settings, approval dialogs, or approval gates. Stop cancels the selected chat and its attached tools. Open **Working → Stop all chats** to stop every chat and pause queued starts. **Ctrl+Alt+Escape** stops the active work and detaches Windows control globally.

## Files attached to a task

Use **Attach files** in Chat, drop files onto the composer, or paste actual clipboard files into the message field. Both pickers offer all files without an extension or MIME allowlist. Ordinary pasted text, HTML and URLs stay text. BLACKICE saves immutable copies with attachment IDs, original names, detected reading capabilities, sizes, and SHA-256 hashes. Changing the original file does not change an existing task attachment. Removing a chip detaches it from the current draft while recorded tasks retain their copies.

**Every file type is attachable.** Office documents, archives, executables, unfamiliar formats, encrypted PDFs, and damaged images are preserved even when the built-in reader cannot interpret them. That limitation appears on the attachment instead of blocking upload. Each file can be at most **10 MiB**, with **10 files** and **50 MiB total** per task. The filename does not establish the actual format. Attaching or exporting a file does not open or execute it.

Built-in readers handle **UTF-8 text**, **PDF page text and search**, and still **PNG, JPEG and WebP** images. PDF pages can also be rendered to PNG for visual inspection, including scanned pages that have no selectable text. There is no automatic OCR. Page/character continuation cursors keep long documents navigable. PDF processing runs locally in bounded worker threads using the bundled PDFium engine, with no runtime download or desktop PDF viewer. It supports up to 2,000 pages, a 20-second operation deadline, bounded text output, and page images with a longest side of 1,600 pixels. Image decoding has separate pixel/data limits; reaching a decoder limit leaves the original file attached. Worker JavaScript heap limits do not establish a strict total limit on PDFium's separate WebAssembly memory.

`relay_files export` makes a separately hashed working copy in the task folder for a compatible local tool. Each export uses a new owned directory and preserves a safe original extension; editing that copy leaves the saved attachment intact. `read_bytes` provides original bytes as base64 in chunks of at most 16 KiB. These actions work across native and API providers with the relevant tools. They do not invent a built-in decoder for every format. Persistent native conversations keep their original attachment schema; start a new task to gain PDF paging, working-copy exports, or byte reads. Fresh relay-only native sessions receive the current schema.

Small text excerpts and file metadata accompany the task. Page images and binary bytes are fetched explicitly, and file contents used by the agent are supplied to the selected model as task data. `relay_files` accepts only IDs attached to the current run. Sending a message, Queue and Save for later wait for pending file copies to finish. A file upload finishes into its original draft even if you switch chats.

## Tools, context, and workflows

All providers receive real workspace tools for reading, writing, listing, searching and running commands in the selected folder. Explicit absolute paths are supported. Command output is bounded, commands time out, and cancellation terminates their process tree. Website actions use the contained browser; native text editing uses the dedicated compatible Notepad adapter.

For an existing text or code file, the workspace `patch` action replaces one uniquely matching `oldText` span with `newText`, preserving surrounding content and its existing line endings, including CRLF. Missing or ambiguous matches fail without changing the file. `patch_history` reads saved before/after revisions in the Relay profile; `undo_patch` restores the earlier bytes only when the current file still matches the recorded result, refusing to overwrite newer edits. Open **workspace menu → File changes**, or find **File changes** with **Ctrl+K**, to inspect these targeted edits and undo them. This history covers the targeted patch action, not every command or full-file write.

Each turn receives capability guidance derived from its actual attached tool catalog, supplied through Codex developer instructions, Responses instructions, Anthropic system instructions or the compatible endpoint's system message. For work, the agent is instructed to choose a suitable tool chain, inspect prerequisites, discover integration schemas and verify the result. Browser, Windows, workspace, attached-file and connected-tool playbooks describe their real capabilities. Current tool-capable tasks require a saved action plan before the answer; one checkable action is enough for a simple reply. Legacy native threads and models without tool support report their planning limitation. This is execution guidance, not a guarantee that a model will choose correctly; failed or unsupported actions still need actual evidence and an honest result.

**Memory & skills** is an editable local library. Agents can save sourced facts and reusable Markdown instructions during work; saved changes become available immediately without a separate approval step. Open an entry's change history for actual **Before** and **After** content, its source chat, and **Undo latest change** or **Restore this revision**. **Deleted** holds recently removed entries for restoration; removed entries are not used by agents. Recent revisions and deleted entries are retained locally within bounded history. Agents see a small metadata catalog and read relevant bodies when needed. `relay_memory` and `relay_skills` also support targeted text patches, so a correction can preserve the rest of an entry. `relay_history` supports previous-task lookup. An ordinary output does not become a memory unless it is saved.

**Workflows** provides the graph editor, templates, model selection per agent, parallel branches, joins, undo/redo, graph diagnostics, measured token usage, traces, safe Markdown results, and JSON import/export. Independent desktop agents can run together; their Windows actions serialize in the shared tool queue. Workflow `maxParallel:null` allows all ready branches; a positive integer sets that workflow’s own concurrency. Graphs no longer have the former 40-node/100-connection ceiling.

## Swarms and operations

Research specialists gather evidence and challenge conclusions. Build teams start one implementation owner alongside independent specialists; additional writers need disjoint scopes. The coordinator integrates results and owns final external-action receipts. Parallel model calls consume their selected accounts' usage; a coordinator's agreement is not independent verification.

Choose **Schedule a task** to describe the work first, then select **Every day**, **Weekdays**, **Every week**, **Every interval**, or **Custom cron**. Calendar schedules use an explicit time zone and show a calculated next-run preview. Custom cron has five fields: minute, hour, day, month, weekday. Working folder, model, overlap and retries remain in optional Task options. **Manage schedules** provides Pause, Resume, Edit and Run now.

Existing workflows can still be scheduled through **Manage schedules → Existing workflows & webhooks → Schedule selected workflow**, with manual and webhook triggers also available. **Schedule on** controls scheduled and webhook admission; **Run now** can admit a manual job while its schedule is off. Every job saves its deployment revision, workflow, task, attachments and trigger data. Editing the deployment affects future jobs, while queued jobs and explicit retries keep their saved definition. Jobs link to durable inbox dispatch receipts and actual runs; they wait for current work to settle and respect a paused inbox.

Automatic retries are **off by default**. You may allow up to three additional attempts with backoff for failed jobs. A known job failure stays local; an uncertain dispatch or interrupted outcome pauses operations for reconciliation. Recorded external-action uncertainty, confirmation or backup recovery holds both automatic and explicit fresh retries; open the original run to inspect and continue with its ledger. A restart also pauses operations; inspect the receipts before choosing **Resume** or an eligible **Retry**. Pause prevents new starts and does not cancel a running job. A chat’s Stop affects that chat. **Stop all chats** pauses operations and the inbox too. Unrecorded external effects still require inspection; model retries cannot guarantee exactly-once delivery.

Schedules run only while Relay is open; this is not an operating-system service. They pause after restart; choose **Manage schedules → Resume** when ready. Missed ticks are not replayed after restart or resume. Each operation chooses **Run together**, **Queue in order**, or **Skip busy schedule ticks** under Task options. New operations default to Run together; existing interval deployments retain their earlier skip policy until edited. Queue keeps due triggers in order and serializes that deployment while other work runs. Skip coalesces busy ticks. This release supports up to 40 saved deployments and 500 unfinished operation jobs. Settled receipts and their delivery identities remain saved within the 48 MiB operations file budget; finishing work frees admission slots without deleting history. Reaching a capacity or byte budget rejects new work while preserving existing records.

For a webhook deployment, **Operations → Webhook** shows its loopback URL (`http://127.0.0.1:<port>/hooks/<deploymentId>`) and bearer token. Send a JSON POST with **`Authorization: Bearer <token>`** and a nonempty **`Idempotency-Key`** header unique to the source event. Repeating a key with identical data returns the original job; reusing it with different data fails. JSON trigger data is limited to 64 KiB and is supplied as task data. The token authenticates delivery; idempotency prevents duplicate job creation, not duplicate side effects inside a model run. BLACKICE must be running. The remote human/agent gateway does not expose this separate webhook route.

## Your agent

**Your agent → Identity & you** edits the real global `SOUL.md` and `USER.md` files under the data directory's `identity` folder. SOUL defines the agent's durable voice and working style; USER holds sourced user facts. Each turn receives an immutable snapshot freshly loaded from disk. Existing files are preserved, external edits are tracked, concurrent edits are detected, and revision history can restore previous content. New profiles do not invent personal facts. Agent and reviewer profile updates require a quote from an actual user message.

**Learning** uses the selected model to review a settled run's task, observed actions, outcome, and optional feedback. It applies evidence-backed memories and reusable skills directly, then injects bounded relevant guidance into later turns. **Learning history** shows the source evidence, actual revisions, editing, removal, restoration and **Undo last change**. Sourced user facts can update `USER.md`; undoing or restoring that learned fact also synchronizes its learned profile content. Recent history is bounded. Learn now, feedback and automatic/manual/off modes remain available. Automatic reviews use model credits and may decide there is nothing durable to learn. Foreground tasks preempt reviews and wait for any admitted writes to settle. This improves local context, skills and profile information; it does not train model weights, upgrade the runtime or rewrite the application. The design follows [Hermes's background reviewer](https://github.com/NousResearch/hermes-agent/blob/main/agent/background_review.py) and [identity model](https://hermes-agent.nousresearch.com/docs/user-guide/features/personality).

**Connected tools** supports MCP stdio and Streamable HTTP servers. Add a local command with explicit arguments or a remote endpoint with optional environment variables / headers. Relay performs the real initialize handshake, discovers tools progressively, and routes calls and results through `relay_connections` across its supported model providers. Local server processes run hidden; stopping a tool drains cancellation. Credentials use the same native encryption as provider keys, or session memory in the source server. Remote OAuth onboarding and legacy HTTP+SSE transport are not implemented; authenticate the server separately or configure headers. The protocol follows the [MCP transport specification](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports).

Use **Connected tools → Import** to paste or choose JSON in the common `{"mcpServers":{...}}` format or a `{"connections":[...]}` array. **Read configuration** shows server names, destinations, argument counts and credential-field counts without revealing credential values or command arguments. **Import servers** adds new IDs without overwriting existing connections. All entries are validated before saving; imported servers remain disconnected until you connect them or an agent uses their tools. Legacy SSE and OAuth configurations are rejected explicitly. Plain credential values are kept only in the import form/request until saved, then use the normal native encryption or source-session storage; source text is cleared when the import is applied or closed. If saving stops partway, Relay reports how many servers were saved so you can inspect the list before importing the remainder.

**Context & continuity** offers Model default, **900k requested**, and custom windows up to 4 million tokens, with output reserve, input headroom, recent-context retention, measured usage, estimates, and compaction checkpoints. Model-reported capacity always takes precedence; selecting 900k does not grant an unsupported window. In this machine's benign live checks, the current Codex route reported **828,400** for both 900k and 1m requests. These were configuration/usage checks, not a full-window load test. Other providers may report a different limit; unreported capacity remains explicitly unverified. Configure model capacity in the provider's model metadata where discovery does not supply it.

Codex keeps its native compaction; remote provider conversations summarize older exchanges using the selected model, retain recent complete tool exchanges, account for summary usage, and preserve the original transcript on disk. Compact context now works on an idle saved conversation. A failed summary leaves the previous working context intact. Long context is not a guarantee of perfect recall.

Persistent Codex conversations retain the tool catalog and schemas they were started with. Current identity and learned guidance are supplied on follow-up, but older persistent conversations need a **new conversation** to gain gateways added later: identity and connected tools in 2.1, task continuity and attachments in 2.2, prompt outlines in 2.17, and the branching task outline/method actions in 2.23. Relay shows a capability note when a saved conversation lacks newer tools. It preserves the genuine conversation instead of copying it into a replacement thread. Relay-only temporary native turns start a new session with the current catalog.

## Local storage paths

Custom prompt templates and their audit revisions are saved in `prompt-templates.json` inside the Relay profile. Portable template exports contain their current definition; the audit stays local.

The desktop app stores history, provider settings, browser profile, and its default workspace in `%APPDATA%\Relay`. Task attachments and their manifests live under `attachments`; saved plans and checkpoints live under `task-state`; conversation turns live under `conversations`; the inbox and operations are persisted in `inbox.json` and `operations.json`. Attachment copies and metadata survive restarts, with integrity checks, backup manifests and per-file recovery records. Codex credentials stay with Codex. Optional API keys and custom header values use Electron safeStorage backed by Windows encryption and are never returned to the interface or included in a distribution. A browser-only source server keeps keys in memory for its current session.

The execution history keeps its most recent 100 runs. The separate conversation archive retains older conversation turns, actual assistant messages and accepted directions, and can reopen them for genuine continuation. Provider transcripts also persist separately so continuations survive restart. Tool traces remain bounded execution history; the archive does not claim to retain every old tool event. Workflow and run backups support recovery. Storage failures are reported rather than silently discarded. The local HTTP server binds loopback and checks its local browser session; webhook delivery uses its deployment token.
