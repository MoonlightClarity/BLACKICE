# BLACKICE 2.39.23

## Use one plan throughout execution

Forced planning now uses one canonical plan of meaningful work items. Preparation, the operational agent, the human editor, continuation, and final review refer to that same plan. The handoff adopts the accepted Plan directly; it no longer asks a second model to translate it into a separate executable outline.

A work item can cover a complete form workflow: inspect its controls, enter several fields, correct validation errors, submit, and verify the outcome. The host records each actual operation automatically. Routine reads, inputs, and tool results advance the operation journal without requiring another model-authored plan leaf or changing the plan's material version.

Canonical criteria now retain the existing optional accuracy contract through normalization and shared Plan projections. A required workflow criterion, including its accuracy metadata, must still match in full. The Plan can represent those inherited requirements while preserving the existing admission guard.

The current planning stages and canonical executor now share guidance that keeps accuracy scoped to its criterion. User-approved substitutions and granularity remain part of the intended result, so an exact count or receipt target does not silently impose literal precision on unrelated form fields. Supported authorized alternatives can be used without another permission request. Later corrections pass through refreshed intent, while independent exact requirements and the inherited-criterion guard remain intact.

## Count results from observed evidence

The canonical contract separates the intended outcome, material plan changes, tool delivery, and external effects. Source coverage is tied to the actual delivered ranges and source version. External counts use confirmed canonical outcome identities; existing records, aliases, duplicate receipts, successful input operations, and successful clicks do not create new completed outcomes.

Observation and judgment criteria can use broad resource scopes when the retained host operation proves that the concrete observation belongs to that scope. Positive judgments reject unrelated citations, and new Plans reject judgment counts that their work items cannot possibly satisfy. Historical Plans and their original evidence remain readable.

Canonical schema guidance now distinguishes resource observations, complete coverage of one concrete source, new destination effects and grounded semantic judgments. Observation counts do not establish how many eligible items a document contains. New-authoring validation rejects source coverage counts above one and scope-only `workspace:` or `origin:` targets, while preserving historical reads and exact host evidence matching.

Browser confirmation adapters bind observed receipt fields to the admitted submission and destination. Ordinary native POST confirmation text has a separate correlation path. A missing or ambiguous receipt remains unverified, and final review cannot replace that uncertainty with a model's claimed success.

The original accepted Plan remains immutable provenance. Final review uses the current task and complete durable journal, including operations omitted from the recent on-screen view. A final-review failure retains confirmed results and reports the incomplete review without publishing an unsupported completion claim.

## Recover without repeating uncertain effects

An interrupted submission remains uncertain until applicable destination evidence resolves it. Conflicting replay stays blocked while independent work and the observations needed for reconciliation can proceed. Explicit HTTP(S) navigation can inspect destination history while still retaining browser-document concurrency protection.

Plans may begin without confirmation matching. Recovery guidance uses actual snapshot records and forms to refine the existing criterion's binding within one cohesive owning work item, with authorized observation and current focus. The executor then re-observes the retained commit. A separate discovery item's read does not establish another item's criterion, and a missing binding does not authorize resubmitting an uncertain effect.

Absence-only status mappings allow an empty `confirmedValues` list only with nonempty, actually observed `absentValues`; both empty is invalid. These mappings cannot confirm success. Positive values require actual observation, and HTTP errors, empty history, or unrelated receipts do not establish absence.

Binding refinement preserves retained facts and their original admitted-operation linkage. An old receipt cannot become a new confirmation or clear a newer pending effect merely because its extraction or status mapping changed. Ambiguous matching remains uncertain; fresh applicable evidence still has to satisfy exact destination, identity, and unique-effect checks.

A separate digest of complete bounded source facts distinguishes a genuinely different observed record from an alias of an earlier receipt, without changing the existing extracted-receipt digest. Only valid differing digests of the same source format bypass that alias guard; all destination, identity and effect checks still apply. Missing or ambiguous metadata remains conservative. A new timestamp or click does not establish a distinct effect, and byte-identical later receipts still need actual request or occurrence correlation.

Cancelled and failed runs retain task-owned live browser documents for an authorized Continue. Exact task, worker, and run ownership still apply, and an explicit handoff to the user remains authoritative. Stop prevents further admission; it does not erase an operation that already reached its destination.

## Keep modes, editors, and provider sessions consistent

Forced requires an applicable owned work item. Scope errors identify missing effects or resources, while an ambiguous choice among matching work items identifies the focus selection that is needed. Advisory permits ordinary work and optional delegation without a mandatory plan. Off requires no plan or canonical journal. Read-only delegated workers retain their restrictions in every mode.

Current canonical planning keeps established workflow ownership, execution configuration and user authorization as constraints or instructions unless the user expressly asks to verify them. Effect guidance includes task-authorized opaque browser behavior within the declared resources; it preserves dependency, evidence and uncertain-effect checks. These clarifications do not grant access to unrelated resources.

The saved Plan screen and task editor can read and edit canonical work items and criteria while preserving local drafts and historical planning records. Save remains separate from Continue. Unrelated edits retain observed confirmation matching; changing that matching requires an explicit edit. Live progress follows the current journal immediately, including after material Plan edits and delayed state updates. Older saved findings remain readable without weakening validation for newly written findings or canonical Plans.

New native sessions capture their exact execution contract and tool catalog. After an explicit contract-change rejection, Retry or Continue opens a fresh session with the same model while preserving the task, plan, and operation journal. A new provider thread does not authorize an uncertain action to run again.

Canonical task guidance now lists the allowed fields for each action and identifies unexpected fields in host rejections. `plan` uses `expectedRevision` and authorable intent, omitting host-owned `contract.planEpoch`; only `focus` and `assess` use top-level `expectedPlanEpoch`. Strict runtime allowlists and captured legacy catalogs remain unchanged.

Shutdown now waits for already admitted connector setup check/confirm responses, including their connector snapshot, to settle after setup closes and before connector dependencies are torn down. Existing probe cancellation and rejection of new requests remain intact.

## Compatibility scope

New browser and workspace workflows use task schema 14 and canonical contract 2. Existing tasks retain their captured schema and tool semantics. VM Workbench workflows explicitly retain schema 13 while their host-effect and control-restoration adapter is ported; their requested planning mode and existing verification obligations remain in force.

An arbitrary AJAX response containing confirmation-like text does not by itself establish a correlated external outcome. A generic file read also does not automatically reconcile a lost filesystem-write response. These cases remain explicit uncertainty boundaries.

## Verification status

The complete Windows source suite passed on the frozen candidate: 650 test files, 7,527 passed tests, 11 permitted optional skips, and no failures. The native city-tolerance Plan-only check also passed through Infer, Feasibility and canonical Plan without starting operational work. Native operational acceptance remains incomplete: provider budget exhaustion and output truncation interrupted attempts, and the latest native attempt was stopped at user direction. This release does not claim full native operational acceptance; partial, failed and stopped attempts remain historical evidence.

Required controlled production-engine acceptance includes a four-outcome validation and lost-response recovery workflow, twenty distinct outcomes with prior records excluded, native text confirmation, unsupported confirmation text, source dependencies and concurrency, cancellation and Continue, binding refinement with retained operation identity, and preservation of confirmed outcomes after final-review failure.

`verification/windows-2.39.23.json` records the complete source suite, while `verification/native-planning-2.39.23.json` records the limited native pass and incomplete operational attempts. Successful hosted build and verification of the exact Windows installer remains a condition of public release. Only after that gate passes will the public release assets include the installer, release manifest, checksums, corresponding native source assets and hosted installation evidence.
