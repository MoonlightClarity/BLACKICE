# Expand a Catalog

Use when adding templates, integrations, products, game items, or other selectable entries.

1. Read the current entries, stable IDs, grouping, and the code or process that uses them.
2. State what each new entry lets the user do and how it differs from the nearest existing choice. Use a variant when only a presentation detail differs.
3. Add the required data and references while keeping unrelated IDs stable.
4. Check every entry for unique identity, valid references, required assets, and correct grouping.
5. Test one representative entry per genuinely shared behavior, plus each entry's unique behavior.
6. Inspect labels and appearance where people choose entries. Check persistence or undo when those features are part of the request.
7. Try an existing neighbor if shared code changed.

Distinguish the claim being delivered: design-only, listed, selectable, or usable for a specified operation. A schema field or label does not establish downstream behavior.

Example: a regional report template must group by region, not merely rename the weekly report. Use data whose weekly and regional totals differ, then inspect the generated output.

If one entry is listed but lacks its runtime behavior, identify that exact gap and continue the working entries. Repair missing references or unsupported branches and rerun their checks. A design-only request does not require building a runtime.

For a batch, report entry, difference, promised operation, observed result, and any remaining gap. Use Verify a Working Slice when a distinct route crosses several components.

Adapted from the Eclipse Roster Expansion method in the Hermes archive.
