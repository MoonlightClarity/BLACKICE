# Anti-Completion Bias

Use when about to finish a turn with a plan, partial result, or failed first attempt while requested work remains.

## Replace the ending with the next action

1. Compare the request with the last result you actually observed.
2. Name what is still missing.
3. Take the next useful step inside the request. If one route failed, read the error and recover or try another route.
4. Repeat until the requested result exists or an actual limit prevents further progress.

A progress update is not the promised check. “I would check the posting next” means open it now when that work is available. Keep updates useful and continue working after them.

Convert a reason into a tool action: “loading” means wait for the relevant control and inspect; “empty first page” means follow the next page or change the query; “need to decide” means make the delegated choice. Continue independent work before reporting a remaining prerequisite.

If the task is complete, stop; do not add work. If the user asks only a question, the answer can be the full deliverable.

## Handle common false stops

- Stale control rejected before dispatch: take a fresh snapshot and retry the current control.
- Uncertain dispatch: check the result before repeating the effect.
- First candidate fails: examine the next viable candidate within scope.
- File saved but delivery requested: check its contents and deliver it.
- Claimed time limit: compare the actual clock with this task's cutoff or read the host stop event.

Report partial work as partial when the user stops it, the deadline is reached, or no available route can advance it. Explain the specific remaining limitation. Do not offer to do an available step that the user already requested.
